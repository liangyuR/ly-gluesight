# PLC 交互表适配决策（plc-table）

依据：《涂胶检测通信交互表20261018_V1.0》（下称“交互表”，PLC 为西门子 S7-200 SMART），对照协议文档 1.3（握手协议 3）与当时代码中的点表模板。适配后握手协议升为 4，协议文档升为修订 2.0，当时的完整差异表已被协议 5 的差异表取代（见 [PLC 通讯协议第 12 节](../integration/plc-communication-protocol.md#12-协议-5-与协议-4交互表-v11-差异)）。

本文件记录交互表中有歧义、需要取舍的项。每条写明问题、可选项、采用的做法及理由、回退方式。第 13 条起为待 PLC 工程师确认的问题清单。

**2026-10-22 起现行为协议 6（分段连拍，点表布局沿用协议 5 的交互表 V1.1，PLC 为 S7-1200），见文末[协议 6 适配](#协议-6-适配分段连拍)；协议 5 的取舍见[协议 5 适配](#协议-5-适配交互表-v11)，其中 P2（协议版本 5）已被协议 6 取代，其余 P1、P3–P6 仍然有效。** 第 1–12 条中关于 S7-200 SMART、DB1、WORD 与 200 SMART 字符串的取舍已被协议 5 取代，保留作历史记录；DInt 序号（第 8 条）、旧数据不兼容读取（第 12 条）与 `resultSn` 头字节复位修复（第 7.2 条中 S7 STRING 部分）仍然有效。

## 1 共享区 DB 号与默认地址

- 问题：交互表为 DB1（原设计 DB100），IP 192.168.2.10、端口 102。S7-200 SMART 没有 DB，只有 V 区，S7 协议把 V 区映射为 DB1。
- 可选项：A 继续默认 DB100，现场改号；B 默认 DB1、可改号；C 固定 DB1。
- 采用：B。默认模板 DB1、主机 192.168.2.10、端口 102；“载入一期 S7 点表”选 S7-200 SMART 时 DB 号锁定为 1，选 S7-1200/1500 时仍可改号。
- 理由：S7-200 SMART 只能是 DB1，默认值即现场值；保留改号能力给 1200/1500。
- 回退：`inspection::DEFAULT_DB`、`DEFAULT_PLC_HOST` 改回原值；对话框去掉锁定。

## 2 S7-200 SMART 连接参数

- 问题：交互表未给机架、插槽、TSAP、连接类型。
- 现状核对：ly-plc 的 S7 驱动已支持指定本地 / 远端 TSAP、连接类型和 PDU 协商，`V` 区地址等价 `DB1`，无需新增连接能力。
- 可选项：A 机架 0 / 插槽 1，PG 连接（TSAP 0x0100 / 0x0101）；B 本地 / 远端 TSAP 0x0102 / 0x0201（OP 连接，界面原有 200 SMART 预设）；C 0x1000 / 0x0300（部分第三方库的 200 SMART 默认值）。
- 采用：B，PDU 请求 240。
- 理由：200 SMART 只有一个 PG 编程连接，PC 占用后 PLC 工程师的 Micro/WIN SMART 可能无法在线；OP（HMI）连接有多个。PDU 按 200 SMART 能力取 240，PC 每次轮询分两段读（字节 0–37、64–210），单段不超过 222 字节。
- 回退：PLC 页“连接”区改 TSAP 或在 CPU 预设中选其它型号即可，无需改代码。若 B 被 CPU 拒绝，按 A、C 顺序核对（见问题清单 Q9）。

## 3 协议版本号

> **已被取代（2026-10-23，见 [segment-burst.md](segment-burst.md) D-SB-6、本文 P2 与 P7）**：协议版本先升为 5（P2，交互表 V1.1），再升为 6（P7，分段连拍）；现行 PC 只接受 6（`handshake::PROTOCOL_VERSION = 6`），4 及其他值拒绝。

- 问题：交互表 `protocolVersion` 备注写“固定 2”、`pcProtocolVersion` 写“成功复位后为 2”，这是协议 2 的旧文字；当前协议为 3，交互表又改了 SN 位置、类型和数据类型。
- 可选项：A 按交互表用 2；B 沿用 3；C 升为 4。
- 采用：C，PC 与参考程序均为 4，2、3 及其他值拒绝。
- 理由：版本号用于识别线上布局。2 已代表 UDInt 数值 SN 布局，3 代表 DBB38/88 的 STRING[24] 布局，新布局与两者都不兼容；沿用旧号会让布局不符的 PLC 程序通过版本校验后再以更难懂的方式失败。PLC 写错版本时 PC 报“PLC 协议版本 x 与 PC 4 不一致”，现场一眼可见。
- 回退：`handshake::PROTOCOL_VERSION` 改值，同步参考程序、测试 PLC 与文档。

## 4 resultCode / faultCode 地址

- 问题：交互表写 `DB1.DBD76`、`DB1.DBD78`，类型却是 WORD。DBD 为 4 字节，DBD76 占 76–79、DBD78 占 78–81，两者互相重叠，DBD78 还与 `acceptedSeq`（DBD80）重叠。
- 采用：按笔误处理，使用 `DB1.DBW76`、`DB1.DBW78`（WORD）。
- 理由：只有 DBW 与类型列、相邻字段都一致；原设计也是 DBW76/78。
- 回退：不适用；若 PLC 确认为其它地址，修改模板对应两行。

## 5 SN 是数值还是字符串

- 问题：交互表 `partSn` 类型列为 string、`resultSn` 为 STRING[50]，但 `partSn` 备注仍是“工件数值 SN……不是字符串条码”（协议 2 旧文字）。“PC 设计地址”列也还是协议 2 的 DBD8 / DBD72。
- 采用：字符串。
- 理由：两处类型列与 `resultSn` 的 STRING[50] 一致，备注和“PC 设计地址”列是从旧文档复制的。协议 3 起全链路已是字符串（握手、生产记录、历史查询与显示、CSV 导出），本次无需再改存储结构。
- 回退：若 PLC 坚持数值 SN，需新开协议版本并恢复数值字段，代价较大，先在问题清单 Q6 确认。

## 6 SN 最大长度

- 问题：`partSn` 未给长度，`resultSn` 为 STRING[50]。
- 可选项：A 50；B 保持 24；C 254（字符串上限）。
- 采用：A，两段区域均按 50 字符分配。S7 STRING 编码的 SN 最多 50 字符；200 SMART 字符串编码的 SN 最多 49 字符，长度字节 50 保留用于识别格式错配（见第 7 条）。字符规则不变：ASCII 0x20–0x7E，去首尾空白后非空，原样保存与回显。
- 理由：`resultSn` 必须逐字节回显 `partSn`，两段最大长度必须一致；50 是交互表唯一给出的长度。DBB160 起 51/52 字节不与其它字段重叠。
- 回退：`handshake::SN_MAX_LEN` 与模板地址的 `.50` 一起改；测试 PLC 的 `SN_CAPACITY`、`SN_MAX_LENGTHS` 同步。

## 7 SN 的字符串编码格式

- 问题：S7-200 SMART 的字符串只有 1 个实际长度字节（`STR_CPY`、`S==` 等指令按此格式），没有 1200/1500 `STRING[n]` 的“声明最大长度”字节；而交互表写了 TIA 风格的 `STRING[50]`，协议 3 文档也描述了两个头字节。PLC 程序实际会写哪种格式无法从交互表判断。
- 可选项：A 只支持 S7 STRING（2 字节头）；B 只支持 200 SMART 字符串（1 字节头）；C 两种都支持，点表按 CPU 选默认值，`partSn` 与 `resultSn` 必须同格式。
- 采用：C。ly-plc 新增 `smartString` 数据类型（ly-plc PR #3，0.3.0）；默认模板（S7-200 SMART）用 `smartString`：VB160 实际长度、VB161–210 字符；VB100 实际长度、VB101–150 字符。选 S7-1200/1500 时默认 `string`（STRING[50]，160–211、100–151）。“载入一期 S7 点表”可单独切换 SN 格式。
- 理由：200 SMART 程序最自然的写法是原生字符串，PLC 用 `S==` 直接比较 `resultSn` 与 `partSn`；但无法排除 PLC 工程师照 `STRING[50]` 手工维护两个头字节。
- 回退：现场在“载入一期 S7 点表”改选 SN 格式，或在点位编辑里把两个 SN 点位的数据类型同时改为另一种，无需改代码。

### 7.1 格式选错时的识别

- 问题：两种格式的头字节并不总能区分，格式选错后特定长度的 SN 会被当成有效值，生产记录存下错误 SN，PLC 还会确认回显结果。
  - PLC 写 S7 STRING、PC 选 200 SMART 字符串：PLC 区为 `50, n, c0…`，PC 把声明长度 50 当成实际长度、把 n 当成第一个字符。n=49（字符“1”）时 PC 读到“1”+SN，回写后 PLC 按 STRING 读回正好等于原 SN 而确认；n 为 32–48 时若字符区残留旧的可打印字符，同样会通过。
  - PLC 写 200 SMART 字符串、PC 选 S7 STRING：只有 50 字符的 SN 能通过声明长度校验，其首字符为 0x20–0x32（空格、`!"#$%&'()*+,-./`、`0`–`2`）时被当成实际长度。首字符为“1”时 PC 读到去掉首字符的 49 个字符，回写后 PLC 按原生格式读回正好等于原 SN 而确认。
- 可选项：A 只改文档，靠现场实测发现；B 200 SMART 格式下首字节为 50 且次字节不超过 50 时拒绝；C 200 SMART 格式保留长度字节 50，SN 最多 49 字符；D 定死一种格式，删除对话框里的格式切换。
- 采用：C。PC 按 200 SMART 字符串读到 50 个字符时，按该点位读错误处理：每个轮询周期都检查，与 `partStart` 无关，直接进入视觉故障，并提示核对两端 SN 格式。PLC 按 S7 STRING 写入时声明长度字节恒为 50，所以第一种错配在 PLC 写入 `partSn` 后的首个轮询即报错，与 SN 内容无关。第二种错配只要 PLC 遵守 49 字符上限，声明长度字节就不会是 50，必然报读错误。
- 理由：B 只拒绝真正有歧义的字节组合，但规则要列出 19 个首字符，PLC 侧难以执行，而 50 位数字条码首位为 0–2 时 B、C 都会拒绝；C 的规则是“200 SMART 字符串最多 49 个字符”，好说明也好核对。D 要在 Q5 答复前锁定格式，答复与默认值不同时只能改代码。A 防不住定长 49 字符 SN 每件都悄悄写错追溯记录的情形。
- 残余风险：PLC 用 200 SMART 字符串却写出 50 字符、首字符为 0x20–0x32 的 SN，同时 PC 误选 S7 STRING，仍会错读；需要两处同时出错。调试时按 Q5 用现场最长的真实 SN 走一件，逐字符核对 PC 记录与 PLC 原值。
- 回退：删除 `handshake::Contract::smart_length_reserved` 的读取校验，测试 PLC `SN_MAX_LENGTHS` 的 `smart_string` 改回 `SN_CAPACITY`，文档恢复为 200 SMART 字符串最多 50 字符；此后格式选错只能靠现场实测发现。

### 7.2 PC 区 `resultSn` 头字节异常的复位修复

- 问题：200 SMART 字符串没有声明长度字节，整块清零后读为空串，不再出现协议 3 的“长度头被清零导致读错误”；但 VB100 被其他程序占用或残留旧值时，长度字节可能大于 50（或为第 7.1 条保留的 50）。原先复位时只修复 S7 STRING 的“声明长度不符”，`resultSn` 的其他头字节错误会让每轮读取失败，复位也读不到快照，握手点位又禁止手动写入，只能等 PLC 工程师手工清 VB100。
- 可选项：A 维持只修复 S7 STRING 声明长度；B 两种格式的头字节错误都在显式复位时按空串修复。
- 采用：B。显式复位时，PC 自己所有的 `resultSn` 出现以下任一情况都先写回空串、读回确认并记入复位审计：S7 STRING 声明长度不为 50 或实际长度大于 50；200 SMART 字符串实际长度大于 50 或等于保留值 50。`partSn` 属于 PLC 区，仍须 PLC 恢复。
- 理由：`resultSn` 只在 `done=1` 时有意义，复位会清 `done`，写回空串不影响任何未结结果；PC 每件都会覆盖该区，若真被其他程序占用，修复后会再次报错，问题照样暴露。
- 回退：`handshake::SN_HEADER_ERRORS` 只保留“PLC 字符串声明长度”，`Contract::sn_header_broken` 去掉保留长度分支。

## 8 DInt 有符号与序号上限

- 问题：交互表把 UDInt 改为 DInt（32 位有符号），涉及 `requestSeq`、`planVersion`、`planReserved`、`ackSeq`、`resultSeq`、`acceptedSeq`、`acceptedPlanReserved`。
- 采用：线上类型 DInt（ly-plc `i32`）。PC 只接受 0–2147483647，读到负数按字段越界处理（与 WORD 越界一样进入视觉故障，不截断、不按无符号重解释）；PC 写入同样限制在该范围。`requestSeq` 仍须非零且递增，上限 2147483647；到上限前 PLC 停止发件、处置未结件，在中性基线下把序号清零并显式复位，PC 复位后以 PLC 当前序号为新基线。PC 导出的计划版本超过 2147483647 时拒绝导出。
- 理由：200 SMART 的 `+D`/`INC_DW` 在 2147483647 后溢出为负数，必须由 PLC 在上限前处理；PC 拒收负数可以防止溢出值被当成巨大正序号。WORD 与 UInt 字节相同，PC 仍按 16 位无符号读。
- 回退：模板与契约字段类型改回 `u32`。

## 9 保留区、所有权与 DB 长度

- 采用：PLC 写 0–63 与 160–210（S7 STRING 为 160–211）；PC 写 64–150（S7 STRING 为 64–151）。保留：DBX0.5–0.7、DBB1、DBB8–11、DBB26–31、DBB38–63、DBX64.6–64.7、DBB65、DBB72–75、DBB88–99、DBB152–159。交互表“BTYE”按 BYTE 处理。V 区至少使用到 VB210（S7 STRING 为 VB211）。
- 理由：交互表新列出 DBB38–41 为预留，但 38–63 原是 `partSn`，迁出后整段保留更安全；DBB8–11、72–75 是协议 2 的数值 SN 位置，交互表没列出，仍保留不复用。
- 回退：文档改动，无代码影响。

## 10 离线虚拟 S7 服务

- 采用：离线产线按默认模板（DB1、`smartString`、DInt）建内存；进程内 S7 服务最大 PDU 由 960 改为 240，与 200 SMART 一致；测试 PLC 脚本默认 DB1、PDU 240、`--sn-format smart_string`，可选 `string`。
- 理由：离线与测试环境应暴露与现场相同的报文长度限制和 SN 格式。
- 回退：`offline::s7_server::MAX_PDU` 改回 960；测试 PLC 用 `--pdu-size 960`。

## 11 PLC 参考程序（SCL）

> **已被取代（2026-10-23，见 [segment-burst.md](segment-burst.md) D-SB-26、本文 P13）**：PLC 已换为 S7-1200（协议 5 适配），参考 FB `scripts/s7-handshake/phase1_plc.scl` 现为协议 6 布局（`INT#6`，删去“运动中超过计划数”“结束时不等于计划数”两处 7006，保留计数回退的 7006）。

- 问题：参考 FB 为 TIA SCL，S7-200 SMART 不支持 SCL。
- 采用：SCL 改到协议 4 布局（DInt、String[50]、版本 4、序号上限 2147483647），定位为 1200/1500 的参考和 200 SMART 的逻辑参考；200 SMART 由 PLC 工程师在 Micro/WIN SMART 中按同等逻辑实现。
- 回退：不适用。

## 12 旧数据（D-0）

- 采用：不做兼容读取。旧 `plc.json`（DB100、STRING[24]、UDInt）在校验握手契约时直接报“必须使用 I32 类型……请按单设备 S7 协议 4 模板重新生成点表”，不能连接；在 PLC 页“载入一期 S7 点表”重建。旧握手事务日志中协议 3 的在途请求按版本不符拒绝自动恢复。检测记录里的 SN 本来就是字符串，无需迁移。

## 协议 5 适配（交互表 V1.1）

依据：《涂胶检测通信交互表20261022_V1.1》及现场确认（2026-10-22）：PLC 已由 S7-200 SMART 更换为 S7-1200；16 位字段统一为 Int、地址不变。适配后握手协议升为 5，协议文档升为修订 3.0，逐项差异见 [PLC 通讯协议第 12 节](../integration/plc-communication-protocol.md#12-协议-5-与协议-4交互表-v11-差异)。

### P1 两个 DB 按方向划分

- 问题：交互表把单个 V 区（DB1）拆成 DB4（PLC → 视觉）与 DB2（视觉 → PLC），两区都从字节 0 起紧凑排列；IP 汇总页仍写“数据块 DB1”。
- 采用：按交互表。模板 `s7_phase1_config(plc_db, pc_db)` 默认 DB4 / DB2，两个号都可改但必须不同；“载入一期 S7 点表”只保留 S7-1200 / 1500 预设，分别填 PLC 区与 PC 区 DB 号。
- 理由：按方向分 DB 后双方不再共用任何字节，PLC 块操作误覆盖对方区域的风险只剩“写错 DB”，握手契约的跨方向字节检查照常生效。
- 回退：模板改回单 DB 布局并恢复协议 4 的偏移；不建议，S7-1200 上没有必要。

### P2 协议版本 5

- 问题：布局、16 位类型与 SN 格式都变了，交互表备注仍写“固定 2”。
- 采用：5，其他值拒绝。
- 理由：S7-1200 的 DB 号可随意填写，用协议 4 模板只把 DB 号改成 4 的点表会读到 `protocolVersion=4` 而通过校验，再按旧偏移读出错位数值；升为 5 后在版本校验处直接报不一致。
- 回退：`handshake::PROTOCOL_VERSION` 改值，同步测试 PLC、SCL 与文档。

### P3 16 位字段为 Int

- 问题：交互表 UINT / INT 混写；现场确认统一为 Int、地址不变。
- 采用：`protocolVersion`、`productCode`、`shotCount`、`deviceShots`、`deviceTriggers`、`pcProtocolVersion`、`resultCode`、`faultCode` 点位类型为 `I16`。PC 只接受 0–32767，读到负数与 DInt 负数同样按字段越界进入视觉故障，不截断、不按无符号重解释；PC 写入同样限制在该范围。产品代码上限随之改为 32767（新建配方校验、PLC 对接参数），拍照计划触发数上限 32767。
- 理由：Int 有符号，PLC 运算溢出会写出负值，拒收可防止被当成巨大正数；现场值远小于 32767。
- 回退：模板与契约字段类型改回 `U16`，范围检查改回 0–65535。

### P4 SN 只用 S7 STRING

- 问题：S7-1200 原生 `String[50]` 带声明长度与实际长度两个头字节；协议 4 为 200 SMART 保留的 `smartString` 格式及“49 字符 / 长度字节 50 保留”规则已无对象。
- 采用：`partSn`（DB4.DBB38）与 `resultSn`（DB2.DBB20）都必须是 `String` 类型、最大 50 字符，契约拒绝 `SmartString`；删除格式错配识别分支，SN 1–50 个 ASCII 可打印字符。`resultSn` 头字节异常仍在显式复位时写回空串（`32 00`）修复。
- 理由：只有一种格式时不存在第 7.1 条的错配歧义，规则与 PLC 端 `String[50]` 一一对应。
- 回退：恢复契约对 `SmartString` 的接受及 `smart_length_reserved` 读取校验。

### P5 连接参数与离线服务

- 采用：模板为机架 0 / 插槽 1、TSAP 按机架插槽自动生成、请求 PDU 480（按 CPU 协商）；离线虚拟 S7 服务仍协商 240；测试 PLC 默认 `--plc-db 4 --pc-db 2`，去掉 `--sn-format`。
- 理由：S7-1200 常见协商结果为 240，两个读段（DB4 90 字节、DB2 72 字节）在 240 内都放得下；离线环境按较小 PDU 暴露报文长度限制。
- 回退：PLC 页“连接”区改 PDU / TSAP 即可，无需改代码。

### P6 旧数据

- 采用：不做兼容读取。协议 4 的 `plc.json`（DB1、`U16`、`SmartString`）在校验握手契约时直接报“必须使用 I16 / String 类型……请按单设备 S7 协议 5 模板重新生成点表”；在 PLC 页“载入一期 S7 点表”重建。协议 4 的在途请求按版本不符拒绝自动恢复。已保存的产品代码大于 32767 的配方在 PLC 对接参数处报错，需改代码后重新发布。

## 协议 6 适配（分段连拍）

依据：分段连拍飞拍方案第 18 版（2026-10-22）、实施计划与实现决策补充（2026-10-22，用户已确认），完整决策见 [segment-burst.md](segment-burst.md)。适配后握手协议升为 6，协议文档升为修订 4.0，逐项差异见 [PLC 通讯协议第 13 节](../integration/plc-communication-protocol.md#13-协议-6-与协议-5-差异)。DB4 / DB2 布局、点表模板、字段名与类型、握手顺序、心跳、复位与 SN 规则全部不变，改变的只有计数字段的语义与结束条件。

**本节决策的实现范围：**示教采集（P8、P10、W2、W8 的示教规则，D1）与生产运行时判定（P9 的丢帧告警、P11 的 `short_part`、P12 的 91/96 新语义与区域判定，C3）都已落地。旧拍照点模型只停用不删除：没有段列表的旧拍照点配方，示教采集仍按协议 5 处理（`shotCount` 须为 1–64 且 `deviceShots` 等于它，实发数、各相机收图数与保存数须全部等于它，失败一律 90/94），生产节拍的缺帧（91）、多帧（96）仍按旧拍照点判定，不产生丢帧告警与 `short_part`。

### P7 协议版本 6

- 问题：点表布局没有变，但 `shotCount`、`deviceShots`、`deviceTriggers` 的含义和结束条件变了；协议 5 的 PLC 程序在连续脉冲串下会按“已发数达到计划数”停发，或在结束时按“实发数不等于计划数”判 7006。
- 采用：6，其他值（含 5）拒绝；点表模板不变，协议 5 的点表不需要重新生成。
- 理由：沿用 5 时，旧 PLC 程序通过版本校验后在现场以缺帧或计数故障表现，难以定位；升为 6 后在版本校验处直接报“PLC 协议版本 5 与 PC 6 不一致”。
- 回退：`handshake::PROTOCOL_VERSION` 改回 5，同步测试 PLC、SCL 与文档（不建议，计数语义已无法与协议 5 兼容）。

### P8 `shotCount` / `deviceShots` 为预期总数 ΣN_exp，核对移到接件

- 问题：协议 5 要求两者相等且等于拍照点数，结束时 `deviceTriggers` 必须等于它；连拍每件帧数在 N_exp ± 容差内波动，精确相等不再成立。
- 采用：两者都是预期总数 ΣN_exp。生产请求时 `shotCount`、`deviceShots` 都必须精确等于 PC 当前计划的 ΣN_exp，否则 PC 返回 90/94（接件核对，不再是请求 payload 不合法）；段配方的示教采集不核对，PLC 可填估算值（参考 FB 要求大于 0，见 P10）；请求层不再校验“非零”与“两者相等”。重新标定使 N_exp 或 ΣN_exp 变化时分配新的 `planVersion`，PLC 须同步 `shotCount`/`deviceShots`。旧拍照点配方（没有段列表）的 `shotCount` 仍是其触发次数，接件仍精确核对。
- 理由：保留身份核对，防止 PLC 与 PC 对应不同计划；不再用它做结束校验。
- 回退：恢复请求层两条校验，接件按拍照点数核对。

### P9 `deviceTriggers` 只作参考，结束时不再比较计数

- 问题：脉冲串由相机使能电平决定，实发数与 ΣN_exp 在首尾自然相差 ±1，相机漏收脉冲也会使帧数与 `deviceTriggers` 不同。
- 采用：`deviceTriggers` 只作参考与日志；PC 在 partEnd 时只核对 `partEnd`/`partStart` 有效与请求身份不变，不比较计数；某台相机总帧数与 `deviceTriggers` 相差 > 1 或与另外每一台相机都相差 > 1 记丢帧告警，≤ 1 正常，只告警，不升级故障、不拦停。段配方每台相机的下一件基线取本件见到的最高 SDK 帧号，`deviceTriggers` 不参与；旧拍照点配方的下一件基线规则不变（确认结果时读取实际已发触发数，见 segment-burst D-SB-7）。
- 理由：规格 §3、§5；帧归属以相机帧号为准比以 PLC 计数更可靠。
- 回退：恢复 `verify_part_end` 的计数相等判断（同时需要恢复 PLC 侧结束计数等于计划）。

### P10 示教采集取消 1–64，不核对计数（段配方）

- 适用范围：下面的“采用”针对段配方候选的采集轮次（D1 已实现）。旧拍照点配方候选的采集轮次仍按协议 5：`shotCount` 须为 1–64 且 `deviceShots` 等于 `shotCount`（不符布防失败，进入视觉故障），结束时 `deviceTriggers`、各相机收图数与保存数须全部等于 `shotCount`，采集失败一律返回 90/94（含相机断连、写盘超时、操作员中止）。
- 采用：示教请求的 `shotCount`/`deviceShots` 是估算值，PC 不核对、不限范围（Int 0–32767）；结束时不要求实发数、收图数、保存数相等；每相机写盘队列与内存有上限，超限的帧按缺帧记录并告警，不判采集失败。采集失败码：相机断连或会话变化 90 配 98，写盘超时、等待开始超时、操作员中止 90 配 99（原 90/94）。
- 理由：多轮采集（默认 10 轮）才能求 N_exp 与容差，帧数本来就会波动。
- 参考 FB 对 `DeviceShots <= 0` 判 7004（`phase1_plc.scl` 新件前置检查），与“PC 接受 0–32767”不一致。采用：**文档注明，不改 FB 判定**——示教的估算值须填大于 0 的整数。理由：生产的 ΣN_exp 恒大于 0，示教估算值本来就填预计帧数，没有填 0 的需要；点表没有区分示教与生产的模式字段，FB 无法只对示教放宽，改判定要重新做 TIA 编译与异常注入核对，收益不抵成本。回退：把该条件改成只检查 `PlanVersion`，让 PC 对 `shotCount` 为 0 的生产请求按 90/94 拒收。

### P11 本件未检与提前 partEnd

- 采用：“本件未检”是机器人与 PLC 之间的 DO，不进 DB4/DB2；机器人等不到触发许可时照常涂胶并置该 DO，PLC 对该件不提交 `partStart`（或提前终止），PC 没有该件记录。PLC 提前置 `partEnd` 时，PC 用已收到的帧照常判 OK/NG，整件帧组数 < ΣN_exp − Σtol 时加 `short_part`（疑似提前终止）标记（段配方），历史中单独显示，不改 OK/NG 与结果码。已布防后撤销 `partStart` 仍按握手故障处理。
- 残余风险：可能出现机器人标了未检、PC 记录却写 OK 的情况，现场不能仅凭 `resultCode=1` 放行。备选：`short_part` 时 PC 直接判 ERR（新故障码或沿用 99），需要时再改。

### P12 异常码与结果码语义

- 采用：不新增码。91 缺帧在段配方下只有三台相机整件没有一帧测成才返回（旧拍照点配方的 91/96 判定不变）；单台缺帧标“检测不完整”，不改 OK/NG；96 多余帧对段模型不再使用（帧数越界只记“帧数异常”告警，常量与文档表保留）；92 定位失败只有旧拍照点配方的特征定位使用；94 含 `shotCount`/`deviceShots` 与 ΣN_exp 不符。溢胶按“每帧最大胶宽超过溢胶上限”判，PLC 结果码沿用 NG_WIDTH（14），原因写“溢胶”；气泡、拉丝本阶段不检，结果标“未检项”。

### P13 SCL 参考 FB 与现场草稿

- 采用：`phase1_plc.scl` 的 `INT#5` 全部改为 `INT#6`；删除运动中 `Delta > FrozenDeviceShots` 与结束时 `CurrentTriggers <> FrozenDeviceShots` 两处 7006；保留累计脉冲计数回退的 7006；原先由“超计划”判定间接保证的 `deviceTriggers` ≤ 32767，改为差值超过 32767 时饱和为 32767（Int 不得写出负值）。DB 布局不变。现场草稿 `scripts/s7-handshake/site/gluesight_site.scl`（达到计划数就停发、按“开始拍摄”边沿逐个出脉冲、结束时计数不等判 7006）与连续脉冲串模型冲突，本轮不改，改动点写进 `scripts/s7-handshake/site/README.md` 的“协议 6 需要的改动点”，由 PLC 工程师按改动点修改。
- 理由：规格只点名参考 FB；现场草稿未纳入验证，改动点列清单更稳妥。
- 回退：参考 FB 恢复两处 7006 与版本 5。
