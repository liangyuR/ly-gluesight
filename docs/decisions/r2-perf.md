# 前端性能与内存决策记录（r2-perf）

范围：在线检测页实时帧内存、历史记录与运行日志列表加载态。不改业务逻辑与后端协议。每条写明问题、可选项、采用的做法与理由、回退方式。测量在离线虚拟产线 + 调试构建上进行，机器满载，只能做相对比较。

## P-1 测量 WebView2 内存时不经 Playwright 附着

- 问题：用 Playwright `connectOverCDP` 附着界面后采样进程内存时，Playwright 会对页面启用 CDP `Network` 域，DevTools 随之在渲染进程里缓存每个响应体。Tauri 的 `invoke` 走自定义协议，实时帧原图（每张约 0.53 MB）和快照都算响应，缓存涨到上限（约 200 MB）后不再释放，直到调试会话断开。
- 实测：同一实例、同一时刻，Playwright 附着时渲染进程 `partition_alloc/partitions/buffer` 为 219 MB，断开后用不启用 `Network` 的 CDP 连接再量为 6 MB。
- 采用：内存结论以“原始 CDP”（只用 `Runtime`、`Performance`、`HeapProfiler`、`Tracing`，不启用 `Network`）为准；Playwright 附着的数据只作对照。
- 回退：无代码改动。

## P-2 实时帧改为在查看器的同一块 canvas 上直接绘制

- 问题：在线检测页跟随当前帧显示原图。原实现每读一张实时帧：建 `ImageData` 和新 canvas，`toDataURL("image/png")` 编码，把几百 KB 的 data URL 交给 SVG `<image>`。每张都是一个新的图片资源，浏览器分别在渲染进程（解码缓存 `cc/image_memory`、Blink 堆上的资源与 URL 字符串）和 GPU 进程（`gpu/transfer_cache`、`skia/gpu_resources`）缓存解码结果，各自涨到预算上限后保持，这就是“打开在线检测页后 WebView2 内存升到约 0.7 GB 并保持”的主体；PNG 编码还在主线程上。
- 可选项：
  - A 保持 PNG data URL；
  - B 改成 8 位灰度 BMP + `blob:` 地址，不再显示时 `revokeObjectURL`；
  - C 灰度像素直接 `putImageData` 到查看器里一块常驻 canvas（SVG `foreignObject` 内，沿用原来的缩放平移与叠加层）。
- B 实测：省掉 PNG 编码，但每帧仍是新的图片资源，渲染进程解码缓存与 GPU 传输缓存照样填满，WebView2 合计与原状相当。
- 采用 C：换帧只重画同一块 canvas，复用一份 RGBA 缓冲，不产生新的图片资源，GPU 传输缓存与渲染进程解码缓存不再增长。300 件对比：WebView2 子进程私有内存中位数 646 → 403 MiB，GPU 进程 427 → 220 MiB，每件主线程任务时长 1749 → 1124 ms；1000 件长稳中 DOM、JS 堆与事件监听都有界。`GrayImage` 增加可选的 `pixels`（降采样后的灰度像素），带 `pixels` 时查看器画 canvas，`url` 只作为这张图的标识（`live:N`，保证换帧时仍按原逻辑复位缩放）。
- 范围：只用于在线检测页实时帧（`workspace_live_frame_image`）。示教、历史详情、采集轮次、标定样本仍走 PNG data URL：这些是用户逐张打开，不是持续的帧流。
- 回退：实时帧读取改回 `.then(decodeGray)`，查看器自动回到 `<image>`。

## P-3 实时帧读取节流

- 问题：原实现把帧状态（等待 → 测量中 → 完成）放进读图条件，每帧到达后至少读两次同一张图；读图期间又有新帧时，旧请求照样解码，再按条件丢弃。
- 采用：
  - 只在帧从“等待 / 未到达”变为“已到达”时读一次，之后测量状态变化不再重读（后端在发出该帧快照之前已缓存这张图）；
  - 同一时间只读一张；读图期间选帧变化，读完后只补读最新的一张，中间的跳过；
  - 新图到达前保留本件上一张图（连同它自己的叠加层与标签），不再每帧闪成“正在读取原图”。换件、换配方不保留。
- 回退：`RuntimeFrame` 的 `useLiveImage` 改回按 scope 每次直接读取。

## P-4 不需要后端提供缩略图或再降采样

- 依据：实时帧已按 900×650 上限降采样（1280×1024 → 812×650，每帧 0.53 MB）。修复后前端每帧只有这 0.53 MB 的 IPC 缓冲（随 GC 回收）和一块常驻的 2.1 MB RGBA 画布缓冲；内存主体已不随帧数增长。再降采样会损失现场查看细节，收益不足以改协议。

## P-5 历史记录、运行日志：新查询返回前保留上一次结果

- 问题：切换筛选或翻页时，结果与当前条件不一致就整块置空，统计闪成“共 0 件”，分页条消失后再出现，按钮移位；运行日志页同样如此（“共 0 条”“1 / 1”）。
- 采用：新查询返回前继续显示上一次结果，统计与表格半透明、`aria-busy`；状态文字只在条件变化时显示，生产中每件入库触发的后台刷新不再闪烁。
- 新查询失败时不再显示上一次条件的结果（避免把旧结果当成新条件的结果），只显示错误；统计标题（真机 / 离线 / 候选调试）按所显示结果的来源命名。批量重判、导出在结果未对齐当前条件时禁用。
- 行点击进入详情时，上一条 / 下一条按该列表所属的查询计算。
- 分页范围文字定宽、等宽数字，翻页时按钮不再左右移动。
- 回退：两页的 `stale` 判断改回“条件不一致即置空”。

## P-6 运行日志行键按内容生成

- 问题：行键为 `${ts}-${下标}`。实时跟随时新日志插到最前，所有行下标后移、键全变，100 行整表卸载重建；行内“记录”查到的历史链接（组件状态）每次刷新都丢。
- 采用：键取时间、级别、事件、cycleId、关联字段与内容前 160 字，同键按出现次序编号。
- 回退：改回原键。

## P-7 历史表格吸顶表头的下边框

- 问题：`.table` 为 `border-collapse: collapse`，折叠边框属于表格而不是单元格，吸顶表头滚动后下边框随正文滚走。
- 采用：历史表格单独改为 `border-collapse: separate; border-spacing: 0`。各单元格只有下边框，视觉与原来一致，表头边框随表头吸顶。
- 教训：最初只写了 `.hist-table { … }`，构建后 `styles.css` 里的 `.table { border-collapse: collapse }` 排在 `history.css` 之后，同一优先级后者生效，计算样式仍是 `collapse`，吸顶边框没有生效（只看源码和单元测试看不出来）。改成 `.table.hist-table` 后，在真实 WebView2 里测得计算样式为 `separate`，滚动 220 px 后表头下边线保留。以后给 `.table` 做表格级覆盖都用提高优先级的写法，不依赖样式表顺序。
- 回退：删掉该声明。

## P-8 列表不做虚拟化，SN 输入不防抖

- 依据：历史每页 50 行、运行日志每页 100 行，DOM 节点数有界，1000 件长稳中不增长。翻页与筛选的耗时主要在后端查询，前端渲染不是瓶颈，虚拟化或防抖收益不明显。
- 运行日志查询耗时随日志量线性增长，见 [log-replay.md](log-replay.md) §13。
- 未验证：1000 件长稳中渲染进程私有内存每 100 件仍缓升约 1–3 MiB（JS 堆与 DOM 不变），是否收敛需要 8 小时以上的整班长稳确认。
- 回退：无代码改动。
