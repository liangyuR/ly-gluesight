# 前端性能与内存决策记录（r2-perf）

范围：在线检测页实时帧内存、在线帧格快照、历史记录列表加载态。各项保留现有业务逻辑和后端协议。实时帧与历史列表的测量采用机器满载时的离线虚拟产线调试构建，用于相对比较。

## P-1 测量 WebView2 内存时不经 Playwright 附着

- 问题：用 Playwright `connectOverCDP` 附着界面后采样进程内存时，Playwright 会对页面启用 CDP `Network` 域，DevTools 随之在渲染进程里缓存每个响应体。Tauri 的 `invoke` 走自定义协议，实时帧原图（每张约 0.53 MB）和快照都算响应，缓存涨到上限（约 200 MB）后不再释放，直到调试会话断开。
- 实测：同一实例、同一时刻，Playwright 附着时渲染进程 `partition_alloc/partitions/buffer` 为 219 MB，断开后用不启用 `Network` 的 CDP 连接再量为 6 MB。
- 采用：内存结论以“原始 CDP”（只用 `Runtime`、`Performance`、`HeapProfiler`、`Tracing`，不启用 `Network`）为准；Playwright 附着的数据只作对照。
- 回退：无代码改动。

## P-2 实时帧改为在查看器的同一块 canvas 上直接绘制

- 问题：在线检测页跟随当前帧显示原图。原实现每读一张实时帧：建 `ImageData` 和新 canvas，`toDataURL("image/png")` 编码，把几百 KB 的 data URL 交给 SVG `<image>`。每张都是一个新的图片资源，浏览器分别在渲染进程（解码缓存 `cc/image_memory`、Blink 堆上的资源与 URL 字符串）和 GPU 进程（`gpu/transfer_cache`、`skia/gpu_resources`）缓存解码结果，各自涨到预算上限后保持，这就是“打开在线检测页后 WebView2 内存升到约 0.7 GB 并保持”的主体；PNG 编码还在主线程上。
- 可选项：
  - A 保持 PNG data URL；
  - B 改成 8 位灰度 BMP + `blob:` 地址，不再显示时 `revokeObjectURL`；
  - C 灰度像素直接 `putImageData` 到查看器里一块常驻 canvas（SVG `foreignObject` 内，沿用原来的缩放平移与叠加层）。
- B 实测：省掉 PNG 编码，但每帧仍是新的图片资源，渲染进程解码缓存与 GPU 传输缓存照样填满，WebView2 合计与原状相当。
- 采用 C：换帧只重画同一块 canvas，复用一份 RGBA 缓冲，不产生新的图片资源，GPU 传输缓存与渲染进程解码缓存不再增长。300 件对比：WebView2 子进程私有内存中位数 646 → 403 MiB，GPU 进程 427 → 220 MiB，每件主线程任务时长 1749 → 1124 ms；1000 件长稳中 DOM、JS 堆与事件监听都有界。`GrayImage` 增加可选的 `pixels`（降采样后的灰度像素），带 `pixels` 时查看器画 canvas，`url` 只作为这张图的标识（`live:N`，保证换帧时仍按原逻辑复位缩放）。
- 范围：只用于在线检测页实时帧（`workspace_live_frame_image`）。示教、历史详情、采集轮次、标定样本仍走 PNG data URL：这些是用户逐张打开，不是持续的帧流。
- 回退：实时帧读取改回 `.then(decodeGray)`，查看器自动回到 `<image>`。

## P-3 实时帧读取节流

- 问题：原实现把帧状态（等待 → 测量中 → 完成）放进读图条件，每帧到达后至少读两次同一张图；读图期间又有新帧时，旧请求照样解码，再按条件丢弃。
- 采用：
  - 只在帧从“等待 / 未到达”变为“已到达”时读一次，之后测量状态变化不再重读（后端在发出该帧快照之前已缓存这张图）；
  - 同一时间只读一张；读图期间选帧变化，读完后只补读最新的一张，中间的跳过；
  - 新图到达前保留本件上一张图（连同它自己的叠加层与标签），不再每帧闪成“正在读取原图”。换件、换配方不保留。
- 回退：`RuntimeFrame` 的 `useLiveImage` 改回按 scope 每次直接读取。

## P-4 不需要后端提供缩略图或再降采样

- 依据：实时帧已按 900×650 上限降采样（1280×1024 → 812×650，每帧 0.53 MB）。修复后前端每帧只有这 0.53 MB 的 IPC 缓冲（随 GC 回收）和一块常驻的 2.1 MB RGBA 画布缓冲；内存主体已不随帧数增长。再降采样会损失现场查看细节，收益不足以改协议。

## P-5 历史记录：新查询返回前保留上一次结果

- 问题：切换筛选或翻页时，结果与当前条件不一致就整块置空，统计闪成“共 0 件”，分页条消失后再出现，按钮移位。
- 采用：新查询返回前继续显示上一次结果，统计与表格半透明、`aria-busy`；状态文字只在条件变化时显示，生产中每件入库触发的后台刷新不再闪烁。
- 新查询失败时不再显示上一次条件的结果（避免把旧结果当成新条件的结果），只显示错误；统计只对应当前筛选结果。批量重判、导出在结果未对齐当前条件时禁用。
- 行点击进入详情时，上一条 / 下一条按该列表所属的查询计算。
- 分页范围文字定宽、等宽数字，翻页时按钮不再左右移动。
- 回退：历史页的 `stale` 判断改回“条件不一致即置空”。

## P-7 历史表格吸顶表头的下边框

- 问题：`.table` 为 `border-collapse: collapse`，折叠边框属于表格而不是单元格，吸顶表头滚动后下边框随正文滚走。
- 采用：历史表格单独改为 `border-collapse: separate; border-spacing: 0`。各单元格只有下边框，视觉与原来一致，表头边框随表头吸顶。
- 教训：最初只写了 `.hist-table { … }`，构建后 `styles.css` 里的 `.table { border-collapse: collapse }` 排在 `history.css` 之后，同一优先级后者生效，计算样式仍是 `collapse`，吸顶边框没有生效（只看源码和单元测试看不出来）。改成 `.table.hist-table` 后，在真实 WebView2 里测得计算样式为 `separate`，滚动 220 px 后表头下边线保留。以后给 `.table` 做表格级覆盖都用提高优先级的写法，不依赖样式表顺序。
- 回退：删掉该声明。

## P-8 列表不做虚拟化，SN 输入不防抖

- 依据：历史每页 50 行，DOM 节点数有界，1000 件长稳中不增长。翻页与筛选的耗时主要在后端查询，前端渲染不是瓶颈，虚拟化或防抖收益不明显。
- 未验证：1000 件长稳中渲染进程私有内存每 100 件仍缓升约 1–3 MiB（JS 堆与 DOM 不变），是否收敛需要 8 小时以上的整班长稳确认。
- 回退：无代码改动。

## P-9 在线帧格按测量结果缓存结论

- 采集中首次显示一帧时计算临时结论，后续快照复用。收尾补测切换走廊时清除此帧缓存；补测期间帧格显示测量中，收到新指标后再计算。
- 整件终判后在第一次发布快照时借用本件测量指标生成最终帧格结论，后续发布复用该结果。整件判定和 PLC 结果回写仍先于此步。未参与判定的已测帧继续显示未判定。
- 帧组按现有序号连续构造，直接用已登记的相机帧状态判定帧组完整性。等待、缺帧与生产跳过沿用原口径，快照字段保持一致。
- Windows 调试构建的合成长件对照使用 4,000 帧组、三台相机和每帧 64 个测站，包含缺帧与断胶。采集与终判快照各自的序列化摘要一致。`Part::view` 的 p95 分别为采集重复快照 28.8 → 3.9 ms、首次终判快照 105.0 → 39.4 ms、重复终判快照 121.1 → 6.4 ms。重复场景各采样 100 次，首次终判采样 21 件。
- 独立生产模拟器用发布标定的三相机 5 fps 合成夹具对照优化前后，四批交叉运行，每批 2 件预热和 10 件统计。两版各 20 件均测成每相机 8 帧，均回写 `1/0` 且 SN 回显匹配。模拟 PLC 从工件结束到 `resultSeq` 写入的 p50 为 96.9 → 96.9 ms、p95 为 194.8 → 130.6 ms。从工件结束到读取结果的 p50 为 124.5 → 124.6 ms、p95 为 224.3 → 155.6 ms。优化前正式样本出现一次 868.3 ms 的慢写入，优化后预热也出现一次 529.5 ms 的慢写入。此样本可核对回写链路与典型耗时，尾延迟变化的归因和真实产线耗时待验证。

## P-10 按送测时间检查在途帧超时

首次送测和收尾补测都登记在途帧，收到结果或超时后移除。超时检查从最早送测的帧开始，在首个未到期限的帧处停止。收尾继续等待在途帧完成或超时，迟到的测量结果不覆盖已记录的超时状态。

Windows 未优化测试构建使用三相机、4,000 帧组逐帧送测并即时回调。两版均测成 12,000 帧且无剩余在途帧。每版预热 1 次、统计 5 次，收帧与结果登记合计耗时中位数为 2,648.9 → 90.5 ms。此对照使用合成测量结果，实际相机、图像引擎与 PLC 延迟需独立测量。

## P-11 按帧查找门控开始边沿

门控开始边沿仍按登记顺序保留。帧编号时，只有新鲜读数才参与查找。按登记顺序从后往前，返回属于本件且按触发延时修正后可用于该帧的第一条边沿，直接交给编号器。最新边沿属于下一门控时继续向前查找。通过查找的边沿仍按 D-SB-55 分配槽位，找不到时沿用帧间隔推断。

Windows 使用 `rustc -O` 对门控查询与帧编号单独计时。每相机保留 4,096 条边沿时，三相机、每件 120 帧组、每批 100 件的编号耗时中位数为 83.7 → 1.1 ms，各取 9 批。每相机只保留 1 条边沿时为 1.87 → 1.34 ms。两版帧号和异常场景结果一致。此对照覆盖编号计算，未计相机传输、图像测量或 PLC 回写。

## P-12 复用冻结门控的累计帧组数

进入后续门控时累计此前各门控冻结的槽数。跳过的门控保留零槽，冻结门控仍接收槽数以内的迟到帧。之后直接由累计槽数和当前槽位计算帧组序号。帧到达时按笔预测测量段，复用该相机刚计算出的笔号和笔内槽位，并用接件时计算的示教各笔起点换算。实际笔长超过示教笔长时仍用示教末帧，超出示教笔数时沿用原帧组序号。

Windows `rustc -O` 合成对照各取 11 批，只有帧编号计入耗时。每件 2,048 门控、每门控 2 帧组、三相机，每批 20 件，p50 为 16.56 → 1.51 ms。每件单门控、120 帧组、三相机，每批 1,000 件，p50 为 2.21 → 2.25 ms。两版帧号与各门控槽数一致。按笔预测的行为由周期用例验证，其耗时和 PLC 回写延迟待独立测量。

## P-13 预先构建到帧段预测路由

接件时从本件配方构建各段累计预期帧数与参与检测的相机表。到帧时使用按笔换算后的序号查找首个覆盖该序号的累计边界，再读取相机是否参与本段检测。单段沿用本段，多段缺少预期帧数时无法预测，越界帧沿用末段。检测相机筛选沿用段的跳过和相机限制规则，示教资源仍由各自的就绪与测量流程校验。补测和复测在未分段回退时也使用这套路由。

Windows `rustc -O` 合成对照使用三相机，两版各取 11 组交叉样本。单次热查询的 p50 在 1 段、12 段和 512 段工况分别为 102.27 → 0.98 ns、89.73 → 3.63 ns、331.45 → 7.85 ns。新版每次建表及释放的 p50 分别为 48 ns、116 ns、3.46 µs。两版逐帧路由一致。计时只覆盖路由计算，未计图像测量、传输或 PLC 回写。

## P-14 同一轮相机资源读取复用发布包目录核验

正式件接件的两轮相机检查各自先核验发布包目录，再逐台读取相机标定、解析各段走廊并核对单项资源路径。两轮之间的有界核验仍独立执行。三相机已预热的正常接件路径因此执行三次完整目录核验。校验后的只读视图仅在本轮使用，后续取用与单独查询资源时仍按各自入口重新核验。

Windows 隔离实例使用相同的正式混胶发布包、三相机 5 fps 和每件 8 帧组交叉对照。四批正常生产共 32 件，每批前 2 件预热，两版各统计 12 件，全部测成每相机 8 帧，正常回写 `1/0`。日志接件耗时 `intakeMs` 的 p50 为 19.77 → 18.87 ms，p95 为 23.01 → 23.86 ms，样本未显示尾延迟改善。用已预热的隔离发布包分别验证同长度坏走廊 JSON、额外文件和同长度错误标定，正常生产均拒件且回写 `90/95`，维护模式下的坏走廊件回写 `0/0`。
