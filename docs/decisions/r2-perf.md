# 工作线 r2-perf：在线检测页与历史页的前端性能和内存

本工作线交付两个 PR：在线检测页实时帧内存（`bugfix/inspect-frame-memory`）、历史记录与运行日志列表加载态（`bugfix/history-log-keep-data`）。不改业务逻辑与后端协议。每条写明问题、可选项、采用的做法与理由、回退方式；测量方法与数据见文末。

## P-1 测量 WebView2 内存时不经 Playwright 附着

- 问题：首轮长稳（`scripts/soak/soak.mjs`）用 Playwright `connectOverCDP` 附着界面后采样进程内存。Playwright 会对页面启用 CDP `Network` 域，DevTools 随之在渲染进程里缓存每个响应体。Tauri 的 `invoke` 走自定义协议，实时帧原图（每张约 0.53 MB）和快照都算响应，缓存涨到上限（约 200 MB）后不再释放，直到调试会话断开。
- 实测：同一实例、同一时刻，Playwright 附着时渲染进程 `partition_alloc/partitions/buffer` 为 219 MB，断开后用不启用 `Network` 的 CDP 连接再量为 6 MB。
- 采用：前后对比用两种方式各量一遍。结论以“原始 CDP”（只用 `Runtime`、`Performance`、`HeapProfiler`、`Tracing`，不启用 `Network`）为准；Playwright 附着的数据只用来对照首轮长稳报告。
- 影响：长稳报告中“在线检测页 WebView2 私有内存 0.3 → 1 GB”里约 0.2 GB 来自测量本身；原状的真实值约 0.65–0.74 GB（见文末）。交 r2-test-infra 调整采样方式。
- 回退：无代码改动。

## P-2 实时帧改为在查看器的同一块 canvas 上直接绘制

- 问题：在线检测页跟随当前拍照点显示原图。原实现每读一张实时帧：建 `ImageData` 和新 canvas，`toDataURL("image/png")` 编码，把几百 KB 的 data URL 交给 SVG `<image>`。每张都是一个新的图片资源，浏览器分别在渲染进程（解码缓存 `cc/image_memory`、Blink 堆上的资源与 URL 字符串）和 GPU 进程（`gpu/transfer_cache`、`skia/gpu_resources`）缓存解码结果，各自涨到预算上限后保持，这就是“打开在线检测页后 WebView2 内存升到约 0.7 GB 并保持”的主体；PNG 编码还在主线程上。
- 可选项：
  - A 保持 PNG data URL；
  - B 改成 8 位灰度 BMP + `blob:` 地址，不再显示时 `revokeObjectURL`；
  - C 灰度像素直接 `putImageData` 到查看器里一块常驻 canvas（SVG `foreignObject` 内，沿用原来的缩放平移与叠加层）。
- 先做了 B 并实测：省掉 PNG 编码，但每帧仍是新的图片资源，渲染进程解码缓存 133–163 MB、GPU 传输缓存 158–198 MB 照样填满，WebView2 合计与原状相当（Playwright 附着时 905–958 MiB，原状 893 MiB 均值）。
- 采用 C：换帧只重画同一块 canvas，复用一份 RGBA 缓冲，不产生新的图片资源，GPU 传输缓存与渲染进程解码缓存不再增长（实测见文末）。`GrayImage` 增加可选的 `pixels`（降采样后的灰度像素），带 `pixels` 时查看器画 canvas，`url` 只作为这张图的标识（`live:N`，保证换帧时仍按原逻辑复位缩放）。
- 范围：只改在线检测页实时帧（`workspace_live_image`）。示教、历史详情、整圈采集、标定样本仍走 PNG data URL：这些是用户逐张打开，不是持续的帧流，改动会扩大到配方工作流各页，收益小。
- 回退：`workspaceApi.liveImage` 改回 `.then(decodeGray)`，查看器自动回到 `<image>`。

## P-3 实时帧读取节流

- 问题：原实现把帧状态（等待 → 测量中 → 完成）放进读图条件，每个拍照点到达后至少读两次同一张图；读图期间拍照点又前进时，旧请求照样解码，再按条件丢弃。
- 采用：
  - 只在帧从“等待 / 未到达”变为“已到达”时读一次，之后测量状态变化不再重读（后端在发出该帧快照之前已缓存这张图，见 `cycle.rs` `on_frame` 中的 `retain_live`）；
  - 同一时间只读一张；读图期间选帧变化，读完后只补读最新的一张，中间的跳过；
  - 新图到达前保留本件上一张图（连同它自己的叠加层与标签），不再每帧闪成“正在读取原图”。换件、换配方不保留。
- 回退：`RuntimeFrame` 的 `useLiveImage` 改回按 scope 每次直接读取。

## P-4 不需要后端提供缩略图或再降采样

- 依据：`workspace_live_image` 已按 900×650 上限降采样（1280×1024 → 812×650，每帧 0.53 MB）。修复后前端每帧只有这 0.53 MB 的 IPC 缓冲（随 GC 回收）和一块常驻的 2.1 MB RGBA 画布缓冲；内存主体已不随帧数增长。再降采样会损失现场查看细节，收益不足以改协议。

## P-5 历史记录、运行日志：新查询返回前保留上一次结果

- 问题（#92 遗留）：切换筛选或翻页时，结果与当前条件不一致就整块置空，统计闪成“共 0 件”，分页条消失后再出现，按钮移位；运行日志页同样如此（“共 0 条”“1 / 1”）。
- 采用：新查询返回前继续显示上一次结果，统计与表格半透明、`aria-busy`；状态文字只在条件变化时显示，生产中每件入库触发的后台刷新不再闪烁。
- 新查询失败时不再显示上一次条件的结果（避免把旧结果当成新条件的结果），只显示错误；统计标题（真机 / 离线 / 候选调试）按所显示结果的来源命名。批量重判、导出在结果未对齐当前条件时禁用。
- 行点击进入详情时，上一条 / 下一条按该列表所属的查询计算。
- 分页范围文字定宽、等宽数字，翻页时按钮不再左右移动。
- 回退：两页的 `stale` 判断改回“条件不一致即置空”。

## P-6 运行日志行键按内容生成

- 问题：行键为 `${ts}-${下标}`。实时跟随时新日志插到最前，所有行下标后移、键全变，100 行整表卸载重建；行内“记录”查到的历史链接（组件状态）每次刷新都丢。
- 采用：键取时间、级别、事件、cycleId、拍照点与内容前 160 字，同键按出现次序编号。
- 回退：改回原键。

## P-7 历史表格吸顶表头的下边框

- 问题：`.table` 为 `border-collapse: collapse`，折叠边框属于表格而不是单元格，吸顶表头滚动后下边框随正文滚走。
- 采用：历史表格单独改为 `border-collapse: separate; border-spacing: 0`。各单元格只有下边框，视觉与原来一致，表头边框随表头吸顶。
- 教训：最初只写了 `.hist-table { … }`，构建后 `styles.css` 里的 `.table { border-collapse: collapse }` 排在 `history.css` 之后，同一优先级后者生效，计算样式仍是 `collapse`，吸顶边框没有生效（只看源码和单元测试看不出来）。改成 `.table.hist-table` 后，在真实 WebView2 里测得计算样式为 `separate`，滚动 220 px 后表头下边线保留。以后给 `.table` 做表格级覆盖都用提高优先级的写法，不依赖样式表顺序。
- 回退：删掉该声明。

## P-8 列表不做虚拟化，SN 输入不防抖

- 依据：历史每页 50 行、运行日志每页 100 行，DOM 节点数有界，长稳中不增长（实测见文末“长时间稳定性”）。翻页与筛选的耗时主要在后端查询，前端渲染不是瓶颈，虚拟化或防抖收益不明显。
- 运行日志查询耗时随日志量线性增长（见文末），不属本工作线，列入跨线问题交日志工作线评估。
- 回退：无代码改动。

## 测量方法与数据

### 环境与方法

- 机器：AMD Ryzen 9 5900X（12 核 24 线程）、64 GB 内存；其他工作线并行运行，测量期间机器 CPU 利用率中位数在 93%–100%，只能做相对比较，绝对值不代表现场。
- 被测软件：debug 构建的 GlueSight（Rust 后端不变，只替换前端 `dist`，前后各用一份构建产物）、lyFlow 1.1.0、进程内虚拟 S7 产线 + 实拍样本集回放（模拟 `mmPerPx` 0.112）、配方 SOAK-1（36 个拍照点，12 组示教）；离线连续运行，`shotIntervalMs` 150、`pauseMs` 200，每件 36 帧。
- 前端构建：原状 = origin/main `d4726c1`；在线检测页修复 = `bugfix/inspect-frame-memory`；长稳与列表测量 = 两个分支合并后的构建。
- 采样：用原始 CDP（P-1），只启用 `Runtime`、`Performance`、`HeapProfiler`、`Tracing`。每 30 s 一次：
  - 各 `msedgewebview2` 子进程的 `PrivateMemorySize64`（按进程类型汇总：渲染、GPU、浏览器等）和累计 CPU 时间；
  - 先 `HeapProfiler.collectGarbage` 再读 `JSHeapUsedSize`、`Nodes`（含已脱离文档但未释放的节点）、`JSEventListeners`，另读 `document.getElementsByTagName("*").length`；
  - 页面内 `requestAnimationFrame` 帧间隔（超过 50 ms 记慢帧）与 `longtask`（超过 50 ms）；
  - 中段与结束各做一次 `memory-infra` 转储，看渲染与 GPU 进程的分配器明细。
- 列表页测量：Playwright 驱动界面，同一实例、同一份数据，原状与修复后各跑一遍，`MutationObserver` 统计表格变空与统计变成“共 0”的次数，`longtask` 统计主线程阻塞，`history_query`、`applog_query` 各调 5 次取中位数。

### 长时间稳定性（1000 件，80 分钟）

两个分支合并后的构建，离线连续运行 1000 件（80.2 分钟，机器 CPU 利用率中位数 100%），每 5 分钟在在线检测、历史记录（离线件、全部）、运行日志（默认 1 小时、实时跟随）三页之间轮换，共 125 个样本，每页访问 5–6 次。

| 页面 | 文档元素数 | JS 堆（MiB） | 事件监听数 | 每次访问的 WebView2 私有内存中位数（MiB） |
| --- | --- | --- | --- | --- |
| 在线检测 | 711–915（随当件帧数变化，首尾持平 884 → 879） | 6.0–7.2 | 228 | 415、433、421、435、365、428 |
| 历史记录（50 行） | 903 恒定 | 5.7–6.0 | 235 | 342、357、357、366、356 |
| 运行日志（100 行） | 1738–1888（首尾 1888 → 1852） | 6.1–6.4 | 432–496 | 336、347、349、358、357 |

- 全程：WebView2 私有内存 325–445 MiB（中位数 357），渲染进程 90–152、GPU 进程 149–253 MiB；`Nodes`（GC 后）在各页都有界（在线检测 1140–1373、历史 1931–1958、运行日志 3227–3994），没有已脱离节点的累积；JS 堆每 100 件增长约 0.02–0.03 MiB；事件监听数不随时间增长。DOM 与 JS 都没有泄漏。
- 仍有缓慢上升：渲染进程私有内存在历史页由 94 升到 112 MiB（800 件），运行日志页由 100 升到 120 MiB，在线检测页五次访问依次为 117、123、124、130、117、128 MiB，波动在 ±6 MiB 内；按页回归每 100 件约 +2.4–2.9 MiB（历史、运行日志）、约 +0.9 MiB（在线检测）。同期 JS 堆与 DOM 不变，增长在 Blink 堆与分配器（中段 → 结束 `blink_gc` 46.5 → 57.3 MiB，`cc/tile_memory` 28.9 → 33.8 MiB）。在线检测页的 300 件对比里渲染进程也由 110 升到 122 MiB（原状 146 → 143，缓存吃满后持平），之后 700 件内只再升约 6 MiB，看上去在趋于平缓。两次 `memory-infra` 转储所在的页面不同（中段在历史页，结束在在线检测页），不能直接相减。是否收敛没有证实，需要 8 小时以上的整班长稳确认（未验证项）。
- 脚本因离线产线故障停机自动重启了 140 次（14%），与历史页统计的 ERR 比例相符；抽查最近几条 ERR，原因都是“布防总预算超时”（阶段 plc-arm-confirmed，预算 200 ms，即 soak S-12，r2-plc 的 #132 在调整），没有统计全部，不属本工作线。

| 19,670 | 约 0.3 s | 约 0.3 s | 约 0.1 s |
| 96,186 | 1.3–3.0 s | 1.2–2.5 s | 0.02–0.03 s |

本次离线回放每件约产生 70 条日志（约 34 KB），长稳后 7 天内达 22 万条。现场节拍下日志量会小一个数量级，但“保留 30 天”下的 7 天范围查询仍会变慢。页面加载态已保证翻页期间不闪空，但等待时间仍由后端决定；是否改为分段索引、缓存总数或缩短默认范围，交日志工作线评估。
