# 维护模式、采集版配方、历史件导入与试判（在线投运一期至三期）

依据：[在线投运方案](../architecture/online-commissioning.md)（2026-10-25 定案）与[生产通讯协议 8](../integration/plc-communication-protocol.md) 第八、九节。一期做维护模式采集、采集版配方与录制元数据；二期做历史件导入为采集轮次；三期做试判统计、历史按模式筛选与复核入口。

## 已定（用户确认）

- 采集版配方只能在维护模式下运行；正常模式遇到采集版，本件照常运动，工件结束后回 90/95。
- 不设采集配额：不设磁盘上限、不自动停录、不设目标件数，磁盘由现场负责；在线检测页不显示维护采集进度与维护试判统计卡片。维护警告收在标题栏维护模式按钮的详情浮层中，在线检测页的退出维护入口也在该浮层内。
- 包含试判；不另标记标准件，示教件兼作标准件（[recipe-build-flow](recipe-build-flow.md) RB-3）。

## 实现取舍

- **MM-1 模式按件锁存**：开关写进 `cycle.json` 的 `maintenance`（开启时间与原因），会话在接件（plcState=10）时把 pcMode 锁存进握手日志，接件登记与回写结果都按它。切换从下一件生效，在途件按原模式完成；切换只等配置门（接件登记期间短暂占用），不要求空闲。保存检测设置时沿用当前的维护模式，设置页不会误关。回退：去掉锁存、要求空闲时切换。
- **MM-2 结果码**：维护件回写 PLC 的结果码与异常码都是 0；会话只在锁存 pcMode=1 的事务上接受 0，正常事务拒绝 0（PLC 判非法）。记录的 `plc_code` 也写 0，试判结论留在 verdict 与 faultCode。`plc_code` 是回写码、不属于结论：落库时比较摘要与区域判定只看 verdict、faultCode 与原因，区域判定照常保留，它的 `plcCode` 取回写码 0。
- **MM-3 不能检测的件也回 0**：正常模式下工件结束后回 90 与 faultCode 的情况（找不到配方、配方或发布包问题、相机未就绪等），维护模式下都回结果码 0、PLC 按未检放行，原因记进本件记录（verdict 记 ERR 以免混入合格统计，plc_code 0）。维护期间 PC 只因协议故障置 90。
- **MM-4 采集件只录图**：采集版件照常按相机帧号分组、录全部帧（不论录制设置，试判件同样，见 MM-11），不送测量，收尾只等收尾窗口；不编拍照计划（会话允许维护件无计划接件）、不要求发布包与走廊。
- **MM-5 记录库原地加列**：`parts` 带 `mode` 列（production / maintenanceCollect / maintenanceShadow，默认 production）；没有该列的 9 版项目旧库在并入本机记录库时原地补列（[history-scope](history-scope.md) HS-4），旧记录按 production，不丢记录。当日统计只算 production。
- **MM-6 录制元数据与保留**：`part.json` 新增 `partMode`、`devices`（每台计划相机的 `cameraId`、`cameraConfig`、本次打开实际写入的 `imaging`（没有则取相机保存值）、`deviceSession`）、`plc`（`requestSeq`、`productCode`）；字段名避开已有的 `mode`（录制方式）与 `cameras`（计划相机编号）。维护采集件的录制目录放 `maintenance-collect` 标记文件，按件数与大小的自动清理跳过它们，也不占保留件数。
- **MM-7 日志**：开关记 `op.maintenance`（`action`、`reason`、退出时仍只有采集版的配方 `collectOnly`）。

- **MM-10 补回丢失的区域判定**：此前落库比较连回写码一起比，试判件的 0 与区域判定的真实码不同，记录退回成没有区域的摘要（历史帧格全部按整件结论着色、区域面板为空、按规则重判无区域可判）。启动时在后台补回：对区域为空、有测过的帧的试判件，按记录的配方快照、已存每帧指标与丢帧告警重新划分区域并判定（与在线同一规则）；结论与摘要相同才写回区域判定、整件标记与每帧所属区域，回写码沿用 0；结论不同的跳过并记日志（`记录修复`）。幂等，补回过的不再处理。
- **MM-11 试判件录全部帧**：维护件不论录制设置都录全部帧——采集件是示教与标定的样本，试判件要靠原图复核误判（TR-4）。录制目录按件数与大小的自动清理照常适用于试判件，只有采集件带保留标记（MM-6）。

## 一期未做（已知限制）

- 找不到配方的件不录图（方案写“录全部帧，归到未识别型号”）：没有配方就不知道用哪几台相机，二期按需要再定。
- `part.json` 的 `plc.earlyEnd` 未写：采集版没有 ΣN_exp，判断不了是否提前结束。
- 采集进度的“占用空间”未统计：逐件累加目录大小代价高，后端只统计件数。

## 一期修正

- **MM-8 空闲就绪按维护模式算**：开工就绪报告与空闲节拍共用同一准入（`cycle::run_kind`）：维护模式下采集版算可开工，只核对相机（相机组、单视角、就绪），不要求走廊、ΣN_exp、发布包、生产预热与拍照计划。维护模式下没有可开工配方（含人工选型号时所选配方开不了工）时，就绪报告的配方项降为提示，来件照常登记、按 MM-3 回 0 放行。任何模式下 PC 都不因配方或相机在空闲时撤就绪（[core-flow.md](core-flow.md) D-CF-4）。
- 在线检测页判定卡的“PLC”在维护件上只显示结果码 0，不再拼上试判异常码（PLC 收到的异常码是 0）。
- **MM-9 任何阶段都可软件复位**：按协议 8“PC 在任何状态都可置 99”，真机在线检测页的标题栏始终显示“软件复位”，维护模式与正常模式相同。复位前置检查只看 PLC 连接、故障输出、心跳与协议版本（[r2-plc.md](r2-plc.md) R2P-4），不满足时按钮禁用并写明原因；在途工件、会话空闲、相机、追溯未落盘都不拦。在途时复位：本件按中断记 ERR 98（D-CF-6），PC 置 90 拉低 Line0，复位请求保留，接着置 99（不等记录落盘），PLC 回 0 后置 10，不必再点一次。

## 二期实现取舍（历史件导入为采集轮次）

- **HI-1 只引用录制原图**：`RecipeCaptureHost::import_history` 逐帧核对录制原图（普通文件、长度等于录制尺寸的 PGM），核对按 `origin.cycleId` 在检测记录库查到的录制目录就是这些原图所在的目录，然后只写 `frames.jsonl`（帧的 `path` 为录制目录里的文件名 `{相机}_s{seq:06}.pgm`），最后写 `round.json`；任一步失败删掉本轮目录。不复制也不链接：单件 1～2 GB，复制多占一份盘，硬链接要求同卷，而录制根以后可能在多块盘上。读帧时按 cycleId 查记录库里的录制目录（记录里的绝对路径，录制迁移或随记录导入时由记录库改写），只接受该目录里的文件。
- **HI-2 轮次格式 4**：新轮次写 `format: 4`（帧路径指向录制）；`format: 3`（原图在本轮目录，以前的硬链接或复制）与 `format: 2` 照常读取，不迁移，本轮目录缺图时按来源 cycleId 读录制原图。历史件轮次的 `origin` 为 `{kind: "history", cycleId, recordId, standard}`，已有的手动配置数据轮次 `{kind: "prepared", label}` 照常读取（`capture_fixture` 现在生成仿历史录制件，经导入成为 `history` 轮次，[recipe-build-flow](recipe-build-flow.md)）：两者状态只能是完成，不记 shotCount 与 deviceTriggers；历史件轮次`frames.jsonl` 的帧号取录制帧号（同一相机“帧号 − 帧组序号”须一致才能导入），触发计数不记；`createdAt` 是导入时间。
- **HI-3 可用条件的取法**：列本机全部有录制目录的真机记录（不限项目、配方），按项目、配方、SN、记录日期、判定筛选，每页 50 件，逐件读 `part.json`；导入时按所选记录编号重新取记录核对，不受分页影响；型号按 `plc.productCode` 核对；相机按 `devices[].cameraConfig` 与当前设备配置（`state_value` 口径）逐台比较，不同只提示、不算不可导入；另把“含手动触发帧”“帧号与帧组序号对不上”“录制目录不在真机录制根下”算作不可导入。
- **HI-4 不要求空闲**：导入不占相机与 PLC，只等配置门（不要求节拍空闲，生产进行中也能导入）；在配置门内按候选修订号重新核对所选的每一件，任一件不可用就一件也不导；同一件对同一候选只导一次（按各轮 `origin.cycleId` 去重，重启后仍有效）。逐件导入中途失败时，已导入的轮次保留，错误里列出。
- **HI-5 标准件**：不另标记标准件，示教件兼作标准件（[recipe-build-flow](recipe-build-flow.md) RB-3）。导入写的 `origin.standard` 恒为 false，旧轮次里的标记读入时忽略。
- **HI-6 不与验证样本去重**：候选没有验证样本（[segment-burst](segment-burst.md) D-SB-46），导入的历史件不用与样本去重；检测结果在历史页用任意配方复测核对，示教件本身也能复测。
- **HI-7 日志**：导入记 `op.capture.import`（`recipeId`、所选记录、新轮次）。
- **HI-9 保护被引用的录制**：登记引用（导入示教件，从核对到写好轮次）与清理（滚动清理从查保护目录到删除；按天清理与手动删除从查引用到删除）用同一把引用锁互斥，取锁顺序先于追溯 spool 锁。清理时现查引用，不用 `maintenance-collect` 标记：标记要在换示教件、删候选、删项目、复制与导入项目时逐一增删并按引用计数，漏一处就误删或永不释放，而且它已表示“维护采集件由现场清理”。引用 = 本机任一项目 `recipe-capture/*/round.json` 里 `origin.kind = history` 的 cycleId；录制滚动清理把这些件的录制目录并入保护目录（与待入库目录同一回调），按天清理跳过这些记录（记录与录制都留），历史页手动删除这些记录时拒绝。扫描或查库失败时本次不清理。换示教件、删除候选会删掉轮次，保护随之解除。
- **HI-10 录制上限默认不限**：项目 `cycle.json` 的 `recordKeep`、`recordMaxGb` 为空表示不限，新项目默认不限，设置页每项有“不限”；已有项目存的值不改。按天清理（本机 `historyDays`，默认 180 天）不变。
- **HI-8 帧率列与提前结束提示**：列表的“时长 / 实测帧率（设定）”按 `part.json` 的 `frames[].ts` 计算：时长取各相机首末帧时间差的最大值，实测帧率取各相机（帧数 − 1）/ 时间差的中位数，设定帧率取 `devices[].cameraConfig.frameRate`；实测偏离设定超过 10% 时标黄。本批可比较的件（没有不可用原因，或只因已导入为本候选轮次）不少于 3 件时取其帧组数中位数 M，帧组数 N < 0.9·M 的件加提示“帧组数 N，明显少于本批中位数 M（疑似提前结束）”。提示不阻断导入。DTO `HistoryCandidate` 带 `warnings`、`durationMs`、`measuredFps`、`setFps`。

## 二期未做（已知限制）

- `plc.earlyEnd` 仍未写，整件也不标提前结束；提前结束只有导入列表按帧组数给出的提示（HI-8），由操作员决定是否排除。
- 录制目录被手动删除或来自别的机器（检测记录不在本机）时，示教件只能提示原图不可用，需重新选用示教件；软件不改写已录原图。

## 三期实现取舍（试判）

- **TR-1 统计口径**：`Store::trial_progress` 按配方取试判件（`mode = maintenanceShadow`，当前统计范围的来源）里**最大的配方版本**计数，旧版本的试判件不混进来。OK / 局部超差 / NG / ERR 沿用历史页的分组，NG 按结论细分、多的在前。溢胶沿用 NG_WIDTH，不单列。
- **TR-2 刷新**：试判统计与维护采集进度一起随在线检测快照推送，维护模式下定时（与采集进度同一周期）从记录库重读；在线检测页不展示统计面板。
- **TR-3 复核入口**：在历史页按配方、维护试判、NG 与 ERR 筛选记录后逐件复核。历史页筛选按配方编号，不分版本：同一配方旧版本的试判件也会列出，按记录里的配方版本区分。
- **TR-4 不加复核标记**：误判与否由操作员看图判断，软件不记录复核结论；退出维护模式仍由工程师手动决定（方案第六节）。

## 三期未做（已知限制）

- 隔离实例端到端（维护采集 → 导入 → 分段、示教、试测、发布 → 试判 → 退出后判出 NG）没有跑过。
- 试判件“记录结论为试判 NG、`plc_code` 为 0”在节拍层只测了落库记录保留区域判定（MM-2），没有从接件到回写的端到端回归测试。
