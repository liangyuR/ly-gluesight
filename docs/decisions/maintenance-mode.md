# 维护模式、采集版配方、历史件导入与试判（在线投运一期至三期）

依据：[在线投运方案](../architecture/online-commissioning.md)（2026-10-25 定案）与[生产通讯协议 8](../integration/plc-communication-protocol.md) 第八、九节。一期做维护模式采集、采集版配方与录制元数据；二期做历史件导入为采集轮次与验证样本去重；三期做试判统计、历史按模式筛选与复核入口。

## 已定（用户确认）

- 采集版配方只能在维护模式下运行；正常模式遇到采集版，本件照常运动，工件结束后回 90/95。
- 不设采集配额：不设磁盘上限、不自动停录、不设目标件数，磁盘由现场负责；界面只显示已录件数与完整可用件数。
- 包含试判；不另标记标准件，示教件兼作标准件（[recipe-build-flow](recipe-build-flow.md) RB-3）。

## 实现取舍

- **MM-1 模式按件锁存**：开关写进 `cycle.json` 的 `maintenance`（开启时间与原因），会话在接件（plcState=10）时把 pcMode 锁存进握手日志，接件登记与回写结果都按它。切换从下一件生效，在途件按原模式完成；切换只等配置门（接件登记期间短暂占用），不要求空闲。保存检测设置时沿用当前的维护模式，设置页不会误关。回退：去掉锁存、要求空闲时切换。
- **MM-2 结果码**：维护件回写 PLC 的结果码与异常码都是 0；会话只在锁存 pcMode=1 的事务上接受 0，正常事务拒绝 0（PLC 判非法）。记录的 `plc_code` 也写 0，试判结论留在 verdict 与 faultCode。`plc_code` 是回写码、不属于结论：落库时比较摘要与区域判定只看 verdict、faultCode 与原因，区域判定照常保留，它的 `plcCode` 取回写码 0。
- **MM-3 不能检测的件也回 0**：正常模式下工件结束后回 90 与 faultCode 的情况（找不到配方、配方或发布包问题、相机未就绪等），维护模式下都回结果码 0、PLC 按未检放行，原因记进本件记录（verdict 记 ERR 以免混入合格统计，plc_code 0）。维护期间 PC 只因协议故障置 90。
- **MM-4 采集件只录图**：采集版件照常按相机帧号分组、录全部帧（不论录制设置，试判件同样，见 MM-11），不送测量，收尾只等收尾窗口；不编拍照计划（会话允许维护件无计划接件）、不要求发布包与走廊。
- **MM-5 记录库原地加列**：`inspection.db` 版本仍为 9，`parts` 原地加 `mode` 列（production / maintenanceCollect / maintenanceShadow，默认 production），不重建、不丢旧记录。当日统计只算 production。
- **MM-6 录制元数据与保留**：`part.json` 新增 `partMode`、`devices`（每台计划相机的 `cameraId`、`cameraConfig`、本次打开实际写入的 `imaging`（没有则取相机保存值）、`deviceSession`）、`plc`（`requestSeq`、`productCode`）；字段名避开已有的 `mode`（录制方式）与 `cameras`（计划相机编号）。维护采集件的录制目录放 `maintenance-collect` 标记文件，按件数与大小的自动清理跳过它们，也不占保留件数。
- **MM-7 日志**：开关记 `op.maintenance`（`action`、`reason`、退出时仍只有采集版的配方 `collectOnly`）。

- **MM-10 补回丢失的区域判定**：此前落库比较连回写码一起比，试判件的 0 与区域判定的真实码不同，记录退回成没有区域的摘要（历史帧格全部按整件结论着色、区域面板为空、按规则重判无区域可判）。启动时在后台补回：对区域为空、有测过的帧的试判件，按记录的配方快照、已存每帧指标与丢帧告警重新划分区域并判定（与在线同一规则）；结论与摘要相同才写回区域判定、整件标记与每帧所属区域，回写码沿用 0；结论不同的跳过并记日志（`记录修复`）。幂等，补回过的不再处理。
- **MM-11 试判件录全部帧**：维护件不论录制设置都录全部帧——采集件是示教与标定的样本，试判件要靠原图复核误判（TR-4）。录制目录按件数与大小的自动清理照常适用于试判件，只有采集件带保留标记（MM-6）。

## 一期未做（已知限制）

- 找不到配方的件不录图（方案写“录全部帧，归到未识别型号”）：没有配方就不知道用哪几台相机，二期按需要再定。
- `part.json` 的 `plc.earlyEnd` 未写：采集版没有 ΣN_exp，判断不了是否提前结束。
- 采集进度的“占用空间”未统计：逐件累加目录大小代价高，一期只给件数。

## 一期修正

- **MM-8 空闲就绪按维护模式算**：开工就绪报告与空闲节拍共用同一准入（`cycle::run_kind`）：维护模式下采集版算可开工，只核对相机（相机组、单视角、就绪），不要求走廊、ΣN_exp、发布包、生产预热与拍照计划。维护模式下没有可开工配方（含人工选型号时所选配方开不了工）不再撤就绪，就绪报告的配方项降为提示，来件照常登记、按 MM-3 回 0 放行；在用配方的相机全掉线仍撤就绪。修正前空闲检查按正式版要求，只有采集版时节拍停在故障、PC 撤下就绪。
- 在线检测页判定卡的“PLC”在维护件上只显示结果码 0，不再拼上试判异常码（PLC 收到的异常码是 0）。
- **MM-9 任何阶段都可软件复位**：按协议 8“PC 在任何状态都可置 99”，真机在线检测页始终显示“软件复位”，维护模式与正常模式相同。复位前置检查只看 PLC 连接、心跳、相机就绪与协议版本，不满足时按钮禁用并写明原因；在途工件、会话空闲、追溯未落盘（维护模式每件都录原图，录制收尾期间常见）都不拦。在途时复位：本件按中断记 ERR 98（D-CF-6），PC 置 90 拉低 Line0，复位请求保留；追溯落盘后 PC 接着置 99，PLC 回 0 后置 10，不必再点一次。

## 二期实现取舍（历史件导入为采集轮次）

- **HI-1 硬链接物化**：`RecipeCaptureHost::import_history` 在 `recipe-capture/<新轮次>/{相机}/{seq:06}.pgm` 为每帧建硬链接指向录制原图（先核对是普通文件、长度等于录制尺寸的 PGM），写 `frames.jsonl`，最后写 `round.json`；任一步失败删掉本轮目录（只删链接）。建不了硬链接（跨卷）报错，不退回复制：单件 1～2 GB，复制会悄悄占满资料盘。
- **HI-2 轮次格式 3**：新轮次写 `format: 3`，`format: 2` 照常读取。历史件轮次的 `origin` 为 `{kind: "history", cycleId, recordId, standard}`，已有的手动配置数据轮次 `{kind: "prepared", label}` 照常读取（`capture_fixture` 现在生成仿历史录制件，经导入成为 `history` 轮次，[recipe-build-flow](recipe-build-flow.md)）：两者状态只能是完成，不记 PLC 计划版本、shotCount 与 deviceTriggers；历史件轮次`frames.jsonl` 的帧号取录制帧号（同一相机“帧号 − 帧组序号”须一致才能导入），触发计数不记；`createdAt` 是导入时间。
- **HI-3 可用条件的取法**：只列本配方（记录的 `recipeId` 等于候选编号）最近 200 件有录制目录的真机记录，逐件读 `part.json`；型号按 `plc.productCode` 核对；相机按 `devices[].cameraConfig` 与当前设备配置（`state_value` 口径）逐台比较；另把“含手动触发帧”“帧号与帧组序号对不上”“录制目录不在真机录制根下”算作不可导入。
- **HI-4 不要求空闲**：导入不占相机与 PLC，只等配置门（不要求节拍空闲，生产进行中也能导入）；在配置门内按候选修订号重新核对所选的每一件，任一件不可用就一件也不导；同一件对同一候选只导一次（按各轮 `origin.cycleId` 去重，重启后仍有效）。逐件物化中途失败时，已导入的轮次保留，错误里列出。
- **HI-5 标准件**：不另标记标准件，示教件兼作标准件（[recipe-build-flow](recipe-build-flow.md) RB-3）。导入写的 `origin.standard` 恒为 false，旧轮次里的标记读入时忽略。
- **HI-6 验证样本去重**：运行验证时核对（D-SB-46 后验证可选）：历史样本的 cycleId 已导入为本候选的轮次、且该轮是本候选的示教件，这个样本记不符合并写明原因；只导入未用的件仍可验证。录制有 `devices` 时，计划相机的 `cameraConfig` 须与当前一致。
- **HI-7 日志**：导入记 `op.capture.import`（`recipeId`、所选记录、新轮次）。
- **HI-8 帧率列与提前结束提示**：列表的“时长 / 实测帧率（设定）”按 `part.json` 的 `frames[].ts` 计算：时长取各相机首末帧时间差的最大值，实测帧率取各相机（帧数 − 1）/ 时间差的中位数，设定帧率取 `devices[].cameraConfig.frameRate`；实测偏离设定超过 10% 时标黄。本批可比较的件（没有不可用原因，或只因已导入为本候选轮次）不少于 3 件时取其帧组数中位数 M，帧组数 N < 0.9·M 的件加提示“帧组数 N，明显少于本批中位数 M（疑似提前结束）”。提示不阻断导入。DTO `HistoryCandidate` 带 `warnings`、`durationMs`、`measuredFps`、`setFps`。

## 二期未做（已知限制）

- 采集版件没有 ΣN_exp，`plc.earlyEnd` 仍未写，提前结束只能靠正式版或试判件的“疑似提前终止”标记识别；采集版件只有导入列表按帧组数给出的提示（HI-8），由操作员决定是否排除。
- 硬链接要求录制目录与 `recipe-capture/` 在同一卷（同一项目目录下默认满足）。轮次原图与录制原图是同一份数据，软件不改写已录原图。
- “从历史选用”只看最近 200 件；更早的件不列出。

## 三期实现取舍（试判）

- **TR-1 统计口径**：`Store::trial_progress` 按配方取试判件（`mode = maintenanceShadow`，当前统计范围的来源）里**最大的配方版本**计数，旧版本的试判件不混进来；重新发布即从零算起。OK / 局部超差 / NG / ERR 沿用历史页的分组，NG 按结论细分、多的在前。溢胶沿用 NG_WIDTH，不单列。
- **TR-2 刷新**：试判统计与维护采集进度一起随在线检测快照推送，维护模式下定时（与采集进度同一周期）从记录库重读；退出维护模式后不再显示。
- **TR-3 复核入口**：面板上有 NG 或 ERR 时给“复核”，跳到历史页并预设配方、维护试判、NG 与 ERR、不限日期。历史页筛选按配方编号，不分版本：同一配方旧版本的试判件也会列出，按记录里的配方版本区分。
- **TR-4 不加复核标记**：误判与否由操作员看图判断，软件不记录复核结论；退出维护模式仍由工程师手动决定（方案第六节）。

## 三期未做（已知限制）

- 隔离实例端到端（维护采集 → 导入 → 分段、示教、试测、发布 → 试判 → 退出后判出 NG）没有跑过。
- 试判件“记录结论为试判 NG、`plc_code` 为 0”在节拍层只测了落库记录保留区域判定（MM-2），没有从接件到回写的端到端回归测试。
