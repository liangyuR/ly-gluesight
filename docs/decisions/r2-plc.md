# PLC 会话与重连决策记录（r2-plc）

范围：S7 会话的离线未结事务、主动断开后重连、复位失败原因、握手日志异常、自动复位、心跳判定与 plc.db 事务身份。握手字段与状态机以 [生产通讯协议 8](../integration/plc-communication-protocol.md) 为准，本文不改协议。依赖 ly-plc 0.4.0（PC 输出写入后立即补一轮读回确认用 `poll_now()`，事务上下文用 `set_log_context`）。

## R2P-1 写后立即读回；超时设置越界时重建

**问题**：PC 输出写入后要等下一次轮询（约 2 个周期）才能读回确认，结果回写与故障输出都被拖慢。

**采用**：写入后立即补一轮读（ly-plc `poll_now()`，在持有驱动锁期间发布值并计数），读的区段与常规轮询相同，不另发单点读请求（`handshake::write_confirmed`）。不缩短轮询周期，以免增加 PLC 通讯负担。

**已有设置文件**：启动加载 `config/cycle.json` 时按保存时的同一套范围校验。越界值把原文件备份为 `cycle.invalid-<时间>.json`，按默认值重建，并在日志记一条配置错误。

**回退**：要恢复两次轮询确认，回滚对应提交并把 ly-plc 回到 0.3.0。

## R2P-2 离线事务崩溃死锁：事务记来源，离线事务可进入离线复位

**问题**：离线采集中途崩溃后，程序重启回到真机模式，但握手日志里还留着离线虚拟 PLC 的未结事务。真机 PLC 不在线没法复位，进离线又被“在途事务”拦住，只能人工移走 `state/plc-handshake.json`。

**可选**：① 启动时自动丢弃离线事务；② 握手日志记录来源，离线来源的事务允许进入离线，由虚拟 PLC 按正常流程复位；③ 加一个“清除离线事务”的人工按钮。

**采用**：②。

- 未结事务记 `origin`（`real` / `offline`）。节拍持有链路门时按当前站点模式设置来源，新事务开始时写入日志，复位审计里也会带上。
- 离线来源的未结事务不阻止切换站点模式：进入离线由虚拟 PLC 复位，回到真机由真机 PLC 复位。真机事务、来源不明的事务仍然阻止切换，提示 `requestSeq`、SN 和“需连接真机 PLC 复位”。
- 离线模式下拒绝复位真机事务。启动时日志写明遗留事务的处置路径。

**理由**：复位仍然走审计，离线事务不会被悄悄丢掉；虚拟 PLC 的复位与真机复位同一条路径。① 绕过了复位审计；③ 多一个只在异常时用的入口。没有来源字段的日志一律按真机处理。

**回退**：回滚对应提交。日志里的 `origin` 字段，旧代码会忽略。

## R2P-3 主动断开后自动重连

**问题**：PC 置故障输出时恰好断线，无法确认已撤下就绪，就按设计主动断开通讯，让 PLC 判 PC 心跳失活。但之后程序不再重连，离线期间只能调接口或重启。

**采用**：断开后 3.5 s 自动重连（`RECONNECT_AFTER_STOP`），重连后按 R2P-9 自动复位。

- 3.5 s = PLC 判 PC 心跳失活的 3 s，加一个 PC 心跳周期（500 ms）的余量：即使断开前刚翻转过一次心跳，PLC 也一定先判失活，PC 才会重新连上。
- 期间有人手动重连（连接时间戳变了）或者改了 PLC 配置，就不再自动重连。
- 重连后会话进入“待复位”，未结事务保留。
- 只自动重连一次。重连后仍确认不了撤下就绪或置故障（PLC 能读不能写，如写保护、PC 区被 PLC 程序覆盖），就停在断开，提示检查 PLC 写入后手动连接（`AfterStop::Manual`）。在新连接上确认置故障后计数清零，下一次主动断开照常自动重连。

**理由**：让 PLC 先判失活是主动断开的唯一目的，达到目的后继续断着没有好处。只重连一次，是因为写入持续被拒时每次重连都会再次断开，反复占用 PLC 连接、刷故障事件和连接日志。

**限制**：PC 断开期间操作员点“断开”不起作用，3.5 s 到点后仍会自动重连。链路在重连后的第一次置故障时恰好又断，也按“仍确认不了”处理，需要手动连接；“连接”不要求空闲，有未结事务时也能点。

**回退**：回滚对应提交，恢复为断开后不自动重连。

## R2P-4 复位失败原因与重连后的就绪报告

**问题**：复位被拒时看不出具体原因，不相关的设备问题也会挡住复位；重连后就绪报告的 PLC 项还显示旧的“S7 PLC 未连接”。

**采用**：

- 复位前置检查只看协议条件：PLC 已连接且会话已核对本次连接、故障输出已写入并读回、PLC 心跳已确认、协议版本一致（离线虚拟 PLC 另要求未结事务来自离线）。第一个不满足的原因记在 `SessionView.reset_blocked_reason`，复位被拒时照此提示。相机、配方、追溯与磁盘不在前置检查里，由节拍按本件检测错误处理。S7 会话接口为 `poll(engine, reset_requested)`。
- `SessionView.connection` 记录会话已核对的连接时间戳。就绪报告发现 PLC 已连接、但会话核对的不是这次连接时，PLC 项显示“PLC 已重新连接，S7 会话正在核对新连接（核对后需复位）”。

**回退**：回滚对应提交，就绪报告恢复按节拍故障原因显示。

## R2P-5 心跳按轮询缓存的变化时刻判断

**问题**：节拍被长操作阻塞超过 3 s 时，PC 自己没去观察心跳，也会被算成 PLC 心跳没变，以 error 级记“PLC 心跳超过 3000 ms 未翻转”，并接着让复位被拒。而 ly-plc 的轮询任务照常在跑，缓存里记着 `plcHeartbeat` 每次变化的轮询时刻。

**采用**：

- 两次观察的间隔不超过阈值的 1/3（1 s）时，仍按原规则判断：先按上次翻转判超时，再记这次读数，“翻转间隔超过 3 s 即失活，之后的翻转不能抵消”。
- 间隔超过 1 s 时，视为观察空档，改按缓存里最近一次变化的时刻判断。缓存的变化时刻在前进，就认为 PLC 一直在翻转；不再变化，照样判失活。

**限制**：如果 PLC 心跳的暂停完全落在 PC 的观察空档里，之后又恢复了，PC 发现不了。PLC 侧对 PC 心跳的监视独立进行，不受影响。

**回退**：回滚对应提交，恢复按观察时刻判断。

## R2P-6 离线虚拟 PLC 的复位请求保持到 PC 回就绪

**问题**：视觉未就绪或故障时，虚拟 PLC 只短暂发一次复位请求；视觉如果还没观察到新的心跳翻转，复位会被拒，之后采集或运行一直等到超时。

**采用**：虚拟 PLC 像现场操作员一样置复位请求（plcState=99）并保持，直到读到 pcState=10 或 `ready_timeout`（应用里是 10 s）后撤下（`offline::line::ensure_ready`）。只改虚拟 PLC，真机侧的复位逻辑不变；重复被拒的原因相同时会话只记一次故障。

**回退**：回滚对应提交。

## R2P-7 plc.db 日志带 requestSeq

**问题**：plc.db 没有事务身份，只能按时间窗口猜某条握手信号属于哪一件。

**采用**：ly-plc 0.4.0 的日志上下文。

- S7 会话校验点表时（启动、换配置、进出离线），把 `requestSeq` 设为上下文。
- 之后每条值变化、写入、边沿日志都带 `requestSeq=N`；与 `requestSeq` 同一轮变化的信号也归到新序号下。
- 可以按 `LogQuery.context` 精确查询，PLC 日志页和导出有“事务”列。
- 0.3 建的旧日志库打开时会补上空列，旧记录为空。

**后续建议**：本件时间线现在按时间窗口取 PLC 信号（[log-replay.md](log-replay.md) §6），可以改为按本件 `requestSeq` 精确取。

**回退**：回滚对应提交并把 ly-plc 回到 0.3.x。日志库多出的列不影响旧版本读取。

## R2P-8 PLC 复位信号触发软件复位

**问题**：现场要从 PLC 侧（如 HMI 按钮）清 PC 的故障和启动后的“待复位”，不用走到 PC 前点“软件复位”。协议 8 的 plcState=99 只能从 PLC 自己的故障态（90）发起，PLC 空闲、只有 PC 故障时用不上。

**采用**：DB4 新增 Bool `resetSignal`（默认 DB4.DBX14.0，原保留 Int 的第 0 位，DB4 仍为 68 字节），由 0 变 1 时等同操作员软件复位。

- 节拍每拍先看信号（`PlcSession::reset_signal`），有上升沿就按操作员复位发起，之后的在途件中断（ERR 98）、pcState=99 与等待 PLC 回 0 都走同一条路。
- 同一连接里先读到 0 再读到 1 才算上升沿：连上时已为 1、或一直保持为 1，都不触发。这样信号卡在高电平时不会一连上就清故障。
- 复位前置检查不满足时（即在线检测页按钮置灰的原因）忽略本次信号，写 `s7.reset.request`（`source=plc_signal`、`ok=false`、`error`）。
- 信号是可选点位：没配时功能关闭；配了就按握手字段同样校验类型、方向、DB 地址和重叠。读取出错只当没读到，不让握手故障。旧 plc.json 启动时按 plcState 所在 DB 补上默认地址（补上后点表不合法就不补），保存 PLC 配置后写回。
- PLC 页“握手点位”组里这个点位可以改地址，其余字段仍由模板定义。

**理由**：直接复用软件复位，PLC 只多一个按钮位，不改握手状态机；不复用 plcState=99，因为那条要 PLC 先进故障。

**回退**：回滚对应提交；PLC 侧不再写这一位即可，PC 不读到上升沿不会有动作。

## R2P-9 故障后总是自动复位

**问题**：PC 每次启动、重连 PLC 或出现协议故障后都停在“待复位”或故障，现场要到在线检测页点“软件复位”或按 HMI 复位按钮才能接件；任何故障都不应挡住下一件。

**采用**：没有开关，总是自动复位。节拍每拍在 PLC 复位信号之后问一次 `PlcSession::auto_reset`，满足下列条件就按软件复位发起（`s7.reset.request` 的 `source=auto`），之后的在途件中断、pcState=99、等 PLC 回 0、置 10 都走软件复位同一条路：

- 会话处于“待复位”或故障，不论原因；
- 复位前置检查通过（R2P-4：PLC 已连接、故障输出已写入、PLC 心跳已确认、协议版本一致），且没有进行中的软件复位；条件没满足就等，满足后再发起；
- 有在途件时照样发起：本件按中断记 ERR 98，PC 置 90 拉低 Line0 后接着置 99（D-CF-6）。

退避：连续 3 次立即发起，之后每次至少间隔 30 s；会话离开待复位、故障持续 60 s 后计数清零。PLC 复位信号（R2P-8）、PLC 置 99 和人工软件复位照常可用。

**理由**：PC 内部的问题已改为按件记检测错误，会话只剩协议故障；复位只清 PLC 侧状态，自动发起与操作员点按钮效果相同，在途件按中断记录不会丢。退避避免 PLC 持续拒绝时反复置 99。

**限制**：R2P-3 主动断开后停在断开（`AfterStop::Manual`）时没有连接，不会自动复位，仍需人工连接。运动超时（T_motion）照常先回 ERR 97 再进故障，之后自动复位。

**回退**：回滚对应提交。

## R2P-10 握手日志异常不挡启动

**问题**：`state/plc-handshake.json` 损坏、版本不受支持或在途事务不合法，或残留未提交的 `plc-handshake.pending.tmp` 时，会话无法复位，只能人工移走文件。

**采用**：启动时把有问题的文件改名到旁边保留：损坏或不受支持的日志改为 `plc-handshake.corrupt-<毫秒>.json`，以空日志启动；未提交的临时文件改为 `plc-handshake.pending-<毫秒>.tmp`，按已提交的日志启动。提示记入运行日志，会话照常进入待复位并自动复位。

**理由**：日志只用于恢复在途事务，读不出就无从恢复；保留原文件供人工核对，不让它挡住生产。

**回退**：回滚对应提交。
