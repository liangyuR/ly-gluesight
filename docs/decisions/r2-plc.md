## 复测环境与方法

- **构建**：release 构建并开启 debug-assertions，因为安装版不接受 `GLUESIGHT_DATA_DIR`，隔离实例只能这样跑：`CARGO_PROFILE_RELEASE_DEBUG_ASSERTIONS=true tauri build --no-bundle --config tests/native/tauri-soak-test.json`。基线取 `d4726c1`，对比本线 `feat/arm-budget`。
- **产线**：进程内虚拟 S7，默认点表 PDU 240、每轮两段读、轮询 50 ms；样本集回放 `2026-10-17-normal-sampleset` 副本（模拟当量 0.112 mm/px）；长稳配方 SOAK-1（12 Pose × 3 相机），触发间隔 150 ms，件间 200 ms，本机 lyFlow 1.1.0。
- **测量**：每个构建连续跑约 150 件，取“布防阶段”日志的 trace。测量时 `arm_ms` 临时设为 2000，避免超预算的件被提前拒收，截断分布。
- **负载**：机器同时跑着其他工作线的编译与测试，整机 CPU 平均 92%（每 30 s 采样一次，共 24 次，最低 46%，最高 100%），两轮负载相当。数字只能相对比较，不代表现场专机。
- **进程内基准**：另用一段进程内基准在 release 下只测 S7 会话的布防：300 件，PLC 与 PC 都在本进程。它只打印分位数，不对应任何回归，没有入库；代码保留在提交 `3883b99` 的 `src-tauri/src/offline/arm_bench.rs`，需要时取回到 `offline` 模块下运行。

测量脚本放在本工作线的临时目录，没有入库：先进离线，设置 `arm_ms`，跑 `soak.mjs run`，再从实例日志里汇总各阶段的分位数。

## R2P-1 布防预算：写后立即轮询、日志落盘移出预算、默认 500 ms

**复测结果（ms，p50 / p90 / p99 / max）**

| 阶段 | 基线（156 件） | 本线（151 件） |
| --- | --- | --- |
| 布防总耗时（到 armed 读回确认） | 182.8 / 325.9 / 558.3 / 1010.2 | 38.6 / 58.8 / 176.6 / 263.8 |
| `prepared-verify` | 24.4 / 115.6 / 255.3 / 287.6 | 16.7 / 30.3 / 57.2 / 57.3 |
| `audit-health` | 11.3 / 15.5 / 158.9 / 356.9 | 13.2 / 20.4 / 145.0 / 231.5 |
| `plc-arm-confirmed` | 137.0 / 150.4 / 265.0 / 976.7 | 1.6 / 2.0 / 3.2 / 3.4 |
| `plc-arm-journal`（不计入预算） | 含在上一行 | 8.3 / 12.4 / 116.1 / 153.6 |
| 其余阶段合计 | p99 < 15 | p99 < 15 |

超出预算的件数：基线在 200 ms 下 35 / 155（22.6%），500 ms 下 3 / 155；本线在 200 ms 下 1 / 151（0.7%），500 ms 下 0。

进程内基准（S7 会话本身，release，同样负载，300 件）：基线的读回确认固定等 2 次轮询，p50 121.9、p99 141.4；改为写后立即轮询后，p50 0.3、p99 0.7。落盘在两种版本里都是 p50 约 7、p99 约 210–240，偶发 500–640。

**问题**：`plc-arm-confirmed` 是超预算的主要来源（S-12），其中两块与机器无关：

1. 读回确认要等两次轮询，约 2 个周期。
2. 布防后的握手日志 fsync 也计在预算内，磁盘一忙就抖到几百毫秒。

**可选**：

- ① 只把默认值调大；
- ② 缩短轮询周期；
- ③ 写后立即补一轮读（ly-plc 支持在持有驱动锁期间发布值并计数），并把落盘移出预算；
- ④ 在 ③ 之外把 5 次单点写合成一次多项写。

**采用**：③，默认值改为 500 ms，取值范围限定 100–5000 ms。

- 补的那一轮读，读的正是轮询的两段（字节 0–37、64–210）。布防后核对请求身份和 `partStart` 正好需要这两段，所以不另发单点读请求，这就是“只读必要区段”的含义。
- 布防预算的定义改为：从 PC 确认并记下 partStart 请求起，到布防输出读回确认为止。之后的握手日志落盘失败照样进入视觉故障，只是不再计入预算。崩溃发生在“输出已确认、阶段尚未落盘”之间时，日志里的阶段停在 Validating，重启后同样要明确复位，恢复路径不变。
- 默认 500 ms 的依据：
  - 本线在 92% 负载下的最大值是 264 ms，留出约一倍余量；
  - 真机 S7-200 SMART 每次请求的往返远大于本机回环，布防要 5 次写加一轮两段读，按每次 10–20 ms 估算多出 60–120 ms；
  - 真实相机下发曝光、增益的时间还没测过；
  - PLC 侧 `ArmTimeout` 默认 10 s，500 ms 只占 5%，不会让 PLC 先超时。
- ② 会增加 PLC 通讯负担，200 SMART 只有一个 PG 连接，不采用。④ 要改 ly-plc 的写接口，留作现场实测后的后续项。

**与 PLC 布防等待的关系**：PLC 的 `ArmTimeout` 从 partStart↑ 开始计时，要覆盖下面四段：

- PC 的开始双读确认，约 2 个轮询周期，没有改；
- 请求落盘；
- `arm_ms`；
- 布防落盘。

两次落盘按上面实测的偶发值各约 0.65 s 计，合计最坏约 `arm_ms` + 1.4 s。协议文档第 7 节（Markdown 与 HTML 版）据此写明 ArmTimeout 不得小于 `arm_ms` + 2 s，建议保持默认 10 s；PC 的 `arm_ms` 上限 5000 ms 加上这些开销仍小于 10 s。高负载下 PC 发现 partStart 还会滞后（见下条观察），不要把 ArmTimeout 压到下限。

**观察**：基线测量中有 1 件，虚拟 PLC 等布防等满 5 s 后撤销了请求，而 PC 的布防 trace 只有 425 ms。这说明高负载下节拍循环发现 partStart 本身就滞后了数秒，不属于布防预算。本线那一轮没有再出现。现场专机负载低得多，但仍应在 PLC 侧记录 partStart↑ 到 armed↑ 的实际间隔。

**已有设置文件**：启动加载 `config/cycle.json` 时按保存时的同一套范围校验。旧版允许保存 0 或 10000 这类越界值，加载时把原文件备份为 `cycle.invalid-<时间>.json`，按默认值重建，并在日志记一条配置错误（D-0，不兼容旧值）。范围内的旧值无法和有意设置的值区分，例如旧默认 200，照常沿用；升级前保存过检测设置的机器，要在设置页把布防预算改为 500。

**回退**：`arm_ms` 改回 200 只需改设置。要恢复两次轮询确认，回滚 `feat/arm-budget` 并把 ly-plc 回到 0.3.0。

**现场待办**：在专机上用真机 PLC 与相机重测“布防阶段”日志里 `plcArm` 的写入、确认、落盘耗时，以及 `camera-imaging` 阶段，按“最大值的 2 倍以上”复核 `arm_ms`。

## R2P-2 离线事务崩溃死锁：事务记来源，离线事务可进入离线复位

**问题**：离线采集中途崩溃后，程序重启回到真机模式，但握手日志里还留着离线虚拟 PLC 的未结事务。真机 PLC 不在线没法复位，进离线又被“在途事务”拦住，只能人工移走 `state/plc-handshake.json`（S-13 问题一）。

**可选**：

- ① 启动时自动丢弃离线事务；
- ② 握手日志记录来源，离线来源的事务允许进入离线，由虚拟 PLC 按正常 faultReset 复位；
- ③ 加一个“清除离线事务”的人工按钮。

**采用**：②。

- 未结事务记 `origin`（`real` / `offline`）。节拍持有 PLC 闸门时按当前站点模式设置来源，新事务开始时写入日志，复位审计里也会带上。
- 切换站点模式：
  - 离线来源的未结事务不阻止切换，进入离线由虚拟 PLC 复位，回到真机由真机 PLC 复位。
  - 真机事务、来源不明的事务、日志不可用，仍然阻止切换，提示 `requestSeq`、SN 和“需连接真机 PLC 复位”。
- 离线模式下拒绝复位真机事务。
- 启动时日志写明遗留事务的处置路径。

**理由**：

- 复位仍然走审计、仍然要求 PLC 输入中性，离线事务不会被悄悄丢掉；虚拟 PLC 的复位与真机操作员复位完全同一条路径。
- ① 绕过了复位审计；③ 多一个只在异常时用的入口，不采用。
- 旧日志没有来源字段，按 D-0 不推断来源，一律按真机处理。还没投产，影响仅限开发机。

**回退**：回滚 `bugfix/offline-pending-origin`。日志里多出的 `origin` 字段，旧代码会忽略。

## R2P-3 主动断开后自动重连

**问题**：PC 置故障输出时恰好断线，无法确认已撤销布防，就按设计主动断开通讯，让 PLC 判 PC 心跳失活。但之后程序不再重连，离线期间只能调接口或重启（S-13 问题二）。

**采用**：断开后 3.5 s 自动重连，重连后仍须明确复位。

- 3.5 s = PLC 判 PC 心跳失活的 3 s，加一个 PC 心跳周期（500 ms）的余量。这样即使断开前刚翻转过一次心跳，PLC 也一定先判失活停线，PC 才会重新连上。
- 期间有人手动重连（连接时间戳变了）或者改了 PLC 配置，就不再自动重连。
- 重连后连接会话已更新，会话进入“待复位”，未结事务保留。
- 只自动重连一次。重连后仍确认不了撤销布防或置故障（PLC 能读不能写，如写保护、PC 区被 PLC 程序覆盖），就停在断开，提示检查 PLC 写入后手动连接。在新连接上确认置故障后计数清零，下一次主动断开照常自动重连。

**理由**：让 PLC 先判失活，是主动断开的唯一目的。达到目的后继续断着没有好处，反而让操作员在离线只读页面上无路可走。只重连一次，是因为写入持续被拒时，每次重连都会再次断开（PR #134 审查实测约 3.5 s 一轮），反复占用 PLC 唯一的 PG 连接、刷故障事件和连接日志；有未结事务时“断开”“保存配置”都被拒，操作员停不下这个循环。退避加上限也能止住循环，但多出的几次重连仍是同样的结果，只会拖长定位时间。

**限制**：

- PC 断开期间操作员点“断开”不起作用（本来就是断开状态），3.5 s 到点后仍会自动重连。
- 链路在重连后的第一次置故障时恰好又断，也按“仍确认不了”处理，需要手动连接。“连接”不要求空闲，有未结事务时也能点。离线模式 PLC 页只读，只有向虚拟 S7 持续注入拒写才会走到这一步，此时经接口连接或重启。

**回退**：回滚该提交，恢复为断开后不自动重连。

## R2P-4 复位失败原因与重连后的就绪报告

**问题**：

- 复位被拒时只报“设备尚未就绪”（D-CF-9）。
- 重连后就绪报告的 PLC 项还显示旧的“S7 PLC 未连接”。

**采用**：

- S7 会话新增 `poll_with_devices`，把节拍算出的设备未就绪原因一起传进来。复位被拒时提示“设备尚未就绪，不能复位并置视觉就绪：<原因>”，例如“没有一个配方开得了工（…）”。原来的 `poll_gated(bool)` 保留为包装，避免影响其他调用方。
- `SessionView` 新增 `connection`，记录会话已核对的连接时间戳。就绪报告发现 PLC 已连接，但会话核对的不是这次连接时，PLC 项显示“PLC 已重新连接，S7 会话正在核对新连接（核对后需复位）”。

**调查结论**：

- 在隔离实例上注入断线：PLC 项先显示“离线 S7 服务尚未连接”，约 3 s 后自动重连，下一个节拍就变为“待复位：S7 连接会话已更新…”。这条路径本身是对的。
- 旧原因只出现在“引擎已连上、但节拍还没处理新连接、快照没更新”的窗口里。正常负载下不到 100 ms；高负载下节拍滞后，窗口会拉长到秒级。测试脚本往往一看到 `plc_get_status` 连上就查就绪报告，正好落在这个窗口里。
- 主动断开后不重连的场景，PLC 项本来就一直显示“未连接”，R2P-3 修复后不再出现。

**回退**：回滚该提交，就绪报告恢复按节拍故障原因显示。

## R2P-5 心跳按轮询缓存的变化时刻判断

**问题**：离线运行间隙（整圈采集结束、发布配方后）会以 error 级记“PLC 心跳超过 3000 ms 未翻转”，而虚拟 PLC 的心跳一直在翻转。r2-perf 隔离实例的日志里，两次示教采集释放后约 5 s 各出现一次。这类误报还会接着触发 R2P-6 的复位被拒。

**原因**：心跳只在 PC 节拍每次观察时比较电平。节拍被长操作阻塞超过 3 s 时，PC 自己没去观察，也会被算成 PLC 心跳没变。而 ly-plc 的轮询任务照常在跑，缓存里记着 `plcHeartbeat` 每次变化的轮询时刻（缓存只在值变化时更新时间戳）。

**采用**：

- 两次观察的间隔不超过阈值的 1/3（1 s）时，仍按原规则判断：先按上次翻转判超时，再记这次读数，“翻转间隔超过 3 s 即失活，之后的翻转不能抵消”。
- 间隔超过 1 s 时，视为观察空档，改按缓存里最近一次变化的时刻判断。缓存的变化时刻在前进，就认为 PLC 一直在翻转；缓存不再变化，照样判失活。

**限制**：如果 PLC 心跳的暂停完全落在 PC 的观察空档里，之后又恢复了，PC 发现不了。改动前也区分不了这种情况，只是会一律误报。PLC 侧对 PC 心跳的监视独立进行，不受影响。

**回退**：回滚该提交，恢复按观察时刻判断。

## R2P-6 离线虚拟 PLC 复位被拒后重按

**问题**：心跳故障后开始整圈采集，虚拟 PLC 只发一次 faultReset。视觉如果还没观察到新的心跳翻转，复位会被拒，之后不再重发，采集一直等到超时（r2-test-infra 第 6 轮）。

**可选**：

- ① 复位前先等心跳翻转。但虚拟 PLC 看不到视觉是否已观察到翻转，而且复位被拒的原因不止心跳，还有设备预热等。
- ② 像操作员一样，没就绪就松开再按。

**采用**：②。每次按住 1 s，没就绪就松开再按，直到就绪或 `ready_timeout`（应用里是 10 s）。只改虚拟 PLC，真机侧的复位逻辑不变。重复被拒的原因相同，会话只记一次故障，不会增加日志噪声。

**回退**：回滚该提交。

## R2P-7 plc.db 日志带 requestSeq

**问题**：plc.db 没有事务身份，只能按时间窗口猜某条握手信号属于哪一件。

**采用**：ly-plc 0.4.0 新增日志上下文。

- S7 会话每次校验点表时（启动、换配置、进出离线），把 `requestSeq` 设为上下文。
- 之后每条值变化、写入、边沿日志都带 `requestSeq=N`；与 `requestSeq` 同一轮变化的信号（如新件的 `partStart`）也归到新序号下。
- 可以按 `LogQuery.context` 精确查询，PLC 日志页和导出新增“事务”列。
- 0.3 建的旧日志库打开时会补上空列，旧记录为空。这属于库自身的表结构升级，不是业务数据兼容。

**后续建议（log-replay）**：时间线现在按时间窗口取 PLC 信号，可以改为按本件 `requestSeq` 精确取。

**回退**：回滚该提交并把 ly-plc 回到 0.3.x。日志库多出的列不影响旧版本读取。
