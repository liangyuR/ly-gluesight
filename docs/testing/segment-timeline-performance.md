# 分段时间轴性能验证

验证日期：2026-11-08。使用现场工件 2 的完整示教记录：1294 帧组、三台相机、3882 张 1280×1024 Bayer PGM，127 段，原图共 5,088,323,736 字节（4.74 GiB）。不以合成图或延迟 mock 替代真实读图。

## 结果

前后各三轮，顺序为前、后、后、前、前、后。除滚动外，下表为三轮中位数；滚动为每轮五个未缓存位置、共十五次的中位数。

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 首次段落可操作 | 13.582 s | 0.083 s |
| 首次可见缩略图完成 | 14.605 s | 0.760 s |
| 首开阶段缩略图解码数，含邻页预取 | 3882 | 192 |
| 滚动至未缓存区域后两次动画帧回调 | 31 ms | 9 ms |
| 滚动至未缓存区域，可见缩略图完成 | 31 ms | 991 ms |
| 切到未缓存工件，可见缩略图完成 | 14.357 s | 0.715 s |
| 切回缓存工件，可见缩略图完成 | 0.724 s | 0.025 s |
| 首开阶段私有提交峰值 | 1908.6 MiB | 431.0 MiB |
| 整个流程私有提交峰值 | 4409.2 MiB | 764.1 MiB |
| 整个流程工作集峰值 | 4365.5 MiB | 1107.6 MiB |
| 流程末尾私有提交 | 3553.7 MiB | 756.3 MiB |
| 同时挂载的缩略图格 | 3882 | 84–108 |

首次可见图完成耗时下降约 94.8%，切新件耗时下降约 95.0%，全流程私有提交峰值下降约 82.7%。首次打开三轮原始值为：优化前 16.770 / 14.605 / 14.230 秒，优化后 0.775 / 0.748 / 0.760 秒。

未缓存区域补图是明确取舍：旧版已经付出整件读取成本，滚动时图像立即可用；新版按需解码，十五次补图为 0.797–1.098 秒，期间显示加载占位。界面响应与图像补齐不是同一个指标。两帧回调为响应代理值，包含测量用 DOM 可见性扫描开销，不代表桌面 WebView2 的精确显示延迟。

连续往返同两件四次后，新版各阶段私有提交峰值处于 727.8–772.6 MiB，没有出现本次流程内的持续单调增长；旧版多次切换峰值达到约 4.3 GiB。本实验只验证两个轮次往返，不能据此宣称长时间多工件场景不存在内存泄漏。

## 测量方法与边界

- Windows 11，Intel Core i9-13900K，约 32 GiB RAM；Chrome 157.0.8103.38，1600×1000 视口，设备像素比 1。
- 优化前组件取自 `5781c53c`，优化后取自 `af574e59`。两个版本在同一生产前端构建中切换，使用实际 `SegmentWorkbench`、原图预览及调度逻辑。后端用同一个 Rust 基准程序分别执行原整件缩略图算法和当前范围读取接口。
- Rust 使用仓库默认开发配置：业务 crate 优化级别 2、image 优化级别 3；未使用单元测试的 opt0 覆盖。两版缩略图均为 160×128，本次对照不因输出分辨率不同而获益。
- 每轮启动独立浏览器和 Rust 进程，以清除应用缓存与内存分配器留存；不清空 Windows 文件缓存，因此不是冷磁盘测试。启动已加载壳页面后，再挂载分段区域开始计时，不含应用启动、JavaScript 下载或工件元数据接口耗时。
- 使用实际磁盘图片、真实 Rust 解码和真实 Canvas 渲染，通过只监听本机的 HTTP 桥接传输。它验证核心读图与页面路径，不包含原生 Tauri IPC/WebView2，因此不能把数值当作已安装桌面软件的端到端验收值。
- 工件 A 为真实记录的隔离元数据副本；工件 B 只改变隔离轮次身份，硬链接相同原图。测试只读现场数据，源 `round.json`、`frames.jsonl` 前后 SHA256 一致。
- 每轮流程：首开 A → 滚动到 10%、25%、50%、75%、100%、50%、0% → A 切 B → B 切 A → 再往返四次。每阶段等待相关请求结束后采集稳定状态，额外保留 400 ms 采样时间。六轮共 84 阶段，无页面运行错误。
- 内存每 100 ms 采样，合计专用 Chrome 与 Rust 进程树。私有提交是进程私有已提交内存，不等于物理驻留内存；工作集统计可能重复计算进程间共享页。不强制 GC，保留实际切件产生的瞬时峰值。表中全流程峰值为各轮峰值的中位数，非六轮最大值。

## 复现

原始现场资料与所有结果保存在忽略的 `output/perf-thumbnails/`，不进入版本库。核心产物：`browser-results.json`（六轮计时、请求计数、DOM/JS 指标）、`summary.json`（内存和耗时汇总）、各轮 `*-memory.jsonl`、`*-backend.log` 和截图、`dataset.json`（数据规模及源元数据校验）。`1-after` 为预跑，不纳入正式结果。

选择已完成的源轮次及对应候选工作区，先在全新输出目录准备隔离数据；不要将基准程序的 `--root` 指向现场目录。以下变量由本机实际路径填写：

```powershell
python scripts/Prepare-ThumbnailBenchmarkData.py --source $sourceRound --clone-id $secondRound
python scripts/Prepare-SegmentTimelineBenchmark.py --workspace $workspaceFile --second-round $secondRound --before-ref 5781c53c
cargo build --offline --locked --manifest-path src-tauri/Cargo.toml --target-dir src-tauri/target/thumb-range-check --example thumbnail_benchmark
pnpm exec vite build --config output/perf-thumbnails/harness/vite.config.mjs
node scripts/Benchmark-SegmentTimeline.mjs
```

默认使用 Program Files 下的 Chrome，可通过 `CHROME_PATH` 指定浏览器程序。脚本使用 18778、18779 本机端口；每轮自动关闭浏览器、Rust 服务与内存采样器。准备器拒绝覆盖已有隔离目录；归档既有结果后再创建新一轮实验。
