# 项目热切换设计

> 现状：**已放弃（2026-10-25）**。开发机实测重启式切换约 1.1 秒（见第一节），热切换收益不足以抵消改动量与风险，决定不实施；本文只作为设计与实测记录保留。前置：[项目设计](project.md)一期、二期已实施，当前切换方式是写指针后重启进程。

## 一、目标与取舍

切换项目时不重启进程：保留 lyFlow 引擎、WebView 和 PLC 握手状态，只把项目资料相关的部分换成目标项目，相机组和 PLC 配置不同时才重连设备。

收益主要来自省掉两件事：进程启动加 lyFlow 引擎加载，以及 WebView 冷启动。两种方式都要重新打开相机（相机组相同时热切换可以不重开，见第五节）。**实施前先实测**：用现在的重启式切换，在工控机上分别记录进程退出、lyFlow 就绪、相机出图三个时间点。如果重启总耗时已经在换线可接受的范围内（例如 10 秒以内），热切换的收益不足以抵消它的复杂度和风险，可以不做。

### 实测（2026-10-25，开发机）

隔离 UI 测试实例（调试构建），加载真实 lyFlow 1.1.5 运行库，在两个项目之间来回切换 6 轮，从调用 `project_switch` 起计时：

| 时间点 | 平均 | 范围 |
| --- | --- | --- |
| 旧进程退出 | 0.69 秒 | 0.68～0.72 秒 |
| 新进程主窗口可用（能调用后端命令，当前项目已是目标项目） | 1.02 秒 | 1.01～1.05 秒 |
| lyFlow 就绪（引擎已加载，可测量） | 1.08 秒 | 1.07～1.10 秒 |

开发机没有接海康相机和 PLC，**未包含相机打开到出图、PLC 连接的时间**。这两项无论重启还是热切换都要做（相机组相同时热切换可省掉相机重开，见第五节），所以热切换在开发机上能省下的只有约 1 秒，其中整页重载仍要约 0.3 秒。

结论：不实施（已放弃）。当时列出的复议条件是两项现场数据，留作记录：一是真实三台相机从打开到出图的耗时，二是现场项目之间是否经常共用同一相机组。只有相机重开占大头、而且项目常共用相机组时，第五节“不重开相机”的优化才有明显价值，而这一点只有热切换做得到。

保留重启式切换作为兜底：热切换任何一步失败而且无法回到原项目时，提示并改走重启。

## 二、现状：哪些状态绑定了项目

| 类别 | 位置 | 绑定方式 | 热切换要做的事 |
| --- | --- | --- | --- |
| 当前项目 | `project::ActiveProject` | 启动时托管，之后不可变 | 改为可替换（读写锁），`storage::project(app)` 每次读最新值 |
| 按需取路径的调用方 | `vision.rs` 标定、`workspace.rs` 发布包、`diagnostics.rs`、`workspace/transfer.rs` 等 | 每次调用 `storage::project(app)` | 不用改，随 `ActiveProject` 自动切换 |
| 记录库 | `store::Store`（`conn: Mutex<Connection>`） | 启动时打开 | 新连接准备好后换入锁内 |
| 节拍设置 | `CycleHost.settings_path`、`shared.settings` | 启动时读取 | 读目标项目的 `cycle.json`，换路径和设置，再 `measure::apply_settings` |
| 配方库 | `CycleHost.recipes: RecipeStore` | 启动时按目录打开 | 按目标目录建新实例后换入；计划号文件不变（本机） |
| 录制 | `CycleHost.recorders`（含清理闭包捕获的根目录） | 启动时构造 | 按目标 `records/`、`records-offline/` 重建后换入 |
| 审计 spool | `CycleHost.audit`（写盘线程 + spool） | 启动时打开并恢复 | 切换前要求已清空；换 spool 路径，写盘线程沿用 |
| 磁盘守护 | `CycleHost.disk` | 按根目录测剩余空间 | 同一卷，可不换 |
| 相机组 | `CameraRig.path`、`slots`；`RecipeCaptureHost.root` | 启动时读 `cameras.json` | 换配置路径；用现有 `rebuild` 重建相机槽；采集根目录换到目标项目 |
| PLC | `PlcHost.config_path`、引擎配置 | 启动时读 `plc.json` | 换路径；用离线模式已有的 `apply_config` 流程应用目标配置 |
| 候选工作区 | `WorkspaceHost.root`、`items`、实时帧缓存、比对 | 启动时扫描目录 | 按目标目录重新扫描后换入，清空实时帧与站点缓存 |
| 生产图缓存 | `ProductionHost.entries` | 按配方编号缓存发布包 | 清空（不同项目可能有同编号配方） |
| 离线模式 | `OfflineHost`（保存进入前的真实环境） | 真实环境来自当前项目 | 一期热切换要求先退出离线模式 |
| 本机状态 | PLC / 示教握手、日志、lyFlow 引擎、样本、计划号 | 与项目无关 | 不动 |
| 前端 | 各页面状态、工作区上下文、PLC/相机订阅 | 进程内缓存 | 切换完成后整页重载 |

## 三、切换流程：准备、提交、应用设备

切换分三段。只有准备段会失败而且失败时什么都没改；提交段只做内存替换；设备段失败不回滚项目，和启动时设备连不上的处理一样。

```text
检查 ─► 准备（只读目标项目，构造新对象） ─► 提交（持门、整体替换、写指针） ─► 应用设备（相机、PLC） ─► 通知前端重载
  │            │失败：丢弃新对象，原项目不受影响
  └ 不满足：拒绝并给原因
```

1. **检查**（同现在的切换前置条件，另加两条）：没有在途工件与未结 PLC 事务、没有在采集、示教握手已结束、录制与审计 spool 已写完、前端没有未保存的候选编辑；**另加**：不在离线模式、目标项目可用。
2. **准备**（不持门，可能耗时）：读取目标项目的 `cycle.json`、`cameras.json`、`plc.json`，打开记录库（含版本检查与恢复），打开配方库，扫描候选工作区，打开审计 spool 并确认没有残留。任何一步失败就丢弃已构造的对象，返回原因，原项目照常运行。
3. **提交**（持 `link_gate` 与 `config_gate`，与布防、配置修改、PLC 握手互斥，时间应在毫秒级）：
   - 向 PLC 发布视觉未就绪，避免切换期间接件；
   - 依次换入记录库连接、节拍设置、配方库、录制、审计 spool、候选工作区，清空生产图缓存与实时帧缓存；
   - 换 `ActiveProject`，写 `current-project.json`，写一条 info 日志；
   - 设置“项目已切换”的代次号，见第六节。
4. **应用设备**（释放门之后）：相机组按目标配置重建（相机组相同时见第五节的优化），PLC 应用目标配置并按 `auto_connect` 重连；`measure::apply_settings`；节拍收到 `Refresh` 重新发布快照，就绪后恢复视觉就绪。设备失败的表现与启动时相同：状态栏报错，可在相机页、PLC 页处理。
5. **通知前端**：发 `project://switched`（带新项目编号）。前端显示“正在切换项目…”遮罩，收到事件后整页重载，用新项目的数据重新渲染。

提交段如果中途出错（例如写指针失败），用准备阶段保留的原对象原样换回，指针不变；换回也失败时进入故障状态，提示“项目切换未完成，请重启软件”，并提供重启按钮（即现在的重启式切换）。

## 四、代码改动

原则：在各模块内部加“可替换”的能力，**不改外部调用方的写法**，避免几十处调用点随之改动（`state::<Store>()` 有 44 处，`state::<WorkspaceHost>()` 有 65 处）。

| 模块 | 改动 |
| --- | --- |
| `project.rs` | `ActiveProject` 内部改为 `RwLock<(id, root)>`，提供 `get()`；新增 `project/hot_switch.rs` 负责检查、准备、提交、应用设备与回滚；`project_switch` 先走热切换，失败兜底重启 |
| `storage.rs` | `project(app)`、`project_config(app)` 改读 `ActiveProject::get()` |
| `store.rs` | `Store::replace_from(other)`：把新连接和备份路径换进锁内，返回旧连接以便回滚 |
| `recipe.rs` | `RecipeStore` 的目录改为锁内字段；`replace_from(other)` 整体换入目录、列表、错误与不可用列表 |
| `recorder.rs` | `Recorders` 改为锁内持有两个 `Recorder`，`replace(real, offline)`；清理闭包按新根目录重建 |
| `audit.rs` | `Audit::reopen(path)`：确认当前 spool 为空、写盘线程空闲后，换入新 spool（恢复逻辑与 `Audit::new` 共用） |
| `cycle.rs` | `settings_path` 改为锁内字段；`reload_project(...)` 换入设置、配方库、录制与 spool；清空 `part_recipe` |
| `camera.rs` | `CameraRig.path` 改为锁内字段；`switch_project(app, path, configs)` 复用 `rebuild`；`RecipeCaptureHost::retarget(root)`（要求没有在采集） |
| `plc.rs` | `config_path` 改为锁内字段；`switch_project(app, path, config)` 复用 `apply_config` 流程 |
| `workspace.rs` | `root` 改为锁内字段；`WorkspaceHost::scan(root)` 从 `init` 中抽出，`replace_from(other)` 换入候选并清空实时帧、站点缓存与比对状态 |
| `production.rs` | `ProductionHost::clear()` |
| 前端 | 切换遮罩；监听 `project://switched` 后 `location.reload()`；切换确认框文案改为“不重启软件，相机与 PLC 按目标项目重新连接” |

## 五、相机组相同时不重开相机（可选优化）

两个项目的相机组可能完全一样（编号、序列号、触发设置都相同，项目只是配方不同）。这时 `rebuild` 可以保留已打开的设备和取流，只换配置路径，热切换就能做到秒级完成。比较规则：逐台比较 `CameraConfig`，全部相同才保留；只要有一台不同，就整组重建，不做逐台增量，以免遗留状态。曝光、增益属于配方参数，布防时下发，不影响这项比较。

## 六、并发与一致性

- **门**：提交段持 `link_gate` 与 `config_gate`。节拍的握手、布防、配方与设置修改、相机重配置都要取其中之一，所以提交期间不会发生。
- **界面命令**：读写候选、记录库的界面命令不经过这两把门。前端在点击切换后立即显示遮罩，不再发出命令，直到重载；后端在模块内部加一个代次号（`ActiveProject` 每次切换加一），候选保存、配方保存等写命令携带进入时读到的代次，提交时代次已变就拒绝，提示“项目已切换，请重试”。这样即使有一条命令卡在切换前后，也不会写进另一个项目。
- **后台任务**：历史清理按当前设置运行，取的是切换后的项目；切换前置条件已保证录制与 spool 写完，没有跨项目的在途写入。
- **PLC**：切换期间视觉未就绪，PLC 不会下发新件；握手状态、协议都不变。PLC 地址变化时，`apply_config` 会断开再连接，PLC 一侧看到的现象和重启时一样，只是时间更短。

## 七、测试计划

| 用例 | 防住的问题 | 层级 |
| --- | --- | --- |
| 准备阶段任一步失败（目标记录库损坏、`cycle.json` 无法解析）→ 原项目的记录库、配方库、设置、指针都不变 | 切换失败后停在半切换状态 | `project/hot_switch` 单元测试 |
| 提交后写记录库、保存配方、写录制目录 → 都落在目标项目目录 | 某个模块漏换，资料写回原项目 | 单元测试（临时资料目录） |
| 代次已变的候选保存命令 → 被拒绝 | 切换期间卡住的命令写进另一个项目 | 单元测试 |
| 有在途工件、未写完的录制、离线模式中 → 拒绝热切换 | 打断生产或丢件记录 | 扩展现有 `site::tests` |
| 隔离实例：A→B 热切换后，配方、历史、相机组、PLC 配置都是 B 的；再切回 A，一切照旧；进程号不变 | 端到端正确性，确认没有重启 | 隔离 UI 实例实测 |
| 真机：相机组不同 / 相同两种情况下切换，相机出图、PLC 握手正常 | 设备释放与重连 | 现场实测（无法自动化） |

## 八、分期与工作量

1. **先实测**重启式切换的耗时（第一节）：开发机已测，约 1.1 秒；还缺现场相机打开到出图的耗时，据此决定是否实施。
2. **一期**：第三、四、六节，前端整页重载；离线模式下不允许热切换；失败兜底重启。预计改 12 个后端文件，约 600～900 行，加 4 条单元测试与 1 轮隔离实例实测。
3. **二期（可选）**：第五节相同相机组不重开；离线模式中切换（先退出离线、切换、再按选择重新进入）。
