## 1.1 现场相机（W0 已知）

- 型号：海康 MV-CU013-80GC（负责人提供，按数据手册传感器 SC130GS 对应；以相机标签为准）。1280 × 1024，4.0 µm 像素，全局快门，满分辨率最高 89.9 fps；GigE；Line0 光耦输入（硬触发）、Line1 光耦输出（频闪）、Line2 双向 IO，与现有 `Line0` 触发、`Line1` 频闪配置一致。
- 像素格式只有 Bayer BG 8/10/10Packed/12/12Packed，**没有 Mono8**：现有代码设 Mono8 失败只记警告，取图回调只收 Mono8，因此真机上没有预览、测量拿不到图且原因不明确。由步 0b 解决。
- 数据手册未写明 Chunk 内容（帧计数、触发计数、时间戳是否可选）。需在 MVS 特性树里确认 `ChunkSelector` 的可选项，结论决定步 2 的计数来源。
- 单帧 8 位约 1.31 MB；三台同时触发经同一千兆上行口约需 33 ms 传完。需确认工控机是每台相机一个网口，还是交换机共享上行；并在台架上确认无丢包。（按 1.2 节，现场是一台三目设备，这一条改为按每次触发三幅图的数据量核算。）

## 1.2 三目相机（2026-10-10，W0 已知与待确认）

**已知（负责人告知）**

- 三目相机在 SDK 枚举时只出现为**一个 Device**，不是三台独立相机。
- **一次取图得到三幅图像**（三个视角）；每个拍照点由人工示教从中**选一幅**来检测。

**旁证**

- 早期的海康三目演示数据每帧是 `FrameN_1/2/3.jpg` 三个文件，回放相机已经按“通道”读取（`replay.rs`、`CameraConfig.replay_channel`）。
- V4.3 手册（易思维三相机传感器）同样是每帧三张图、示教时人工挑最合适的一张（手册 p50、p82、p92）。手册不是本现场的系统，只作参考。

**待现场确认（决定步 T 的取图实现）**

1. 三幅图怎么交付：一帧里拼接（上下或左右，各占多大）、按颜色通道打包、SDK 的多部分（multi-part）缓冲，还是同一触发的三次回调？
2. 每幅图的分辨率与像素格式：是否仍是 1280 × 1024、Bayer BG8；1.1 节的 MV-CU013-80GC 是否就是其中的传感器。若三幅按颜色通道打包，步 0b 的 Bayer 转灰度不适用，要改为按通道拆包。
3. 三幅图是否同一时刻曝光；触发输入几路（整个设备一路，还是每个视角一路）；Chunk 的帧计数 / 触发计数是设备级一份，还是每个视角一份。
4. 设备最高帧率与每次触发的数据量（若每幅 1.31 MB，一次约 3.9 MB）；设备到工控机的链路与丢包。
5. 能否只输出选中的视角；不能时生产也要收三幅。录制与历史是三幅都存，还是只存选中的一幅。
6. 现场一共几台三目设备（一台，还是每把胶枪一台）。

**对已完成各步的影响**

- 步 0b：Bayer8 / Mono8 转灰度针对一幅图。三幅拼接时先转换后裁剪即可；按颜色通道打包时需要新的拆包，不能按 Bayer 处理。
- 步 1 / 1b：拍照点的 `camera` 指设备，需新增视角（1–3）；原图指纹、试测指纹与几何哈希都要带上视角；示教页要并排显示三幅、由人工选一幅，再在选中的那幅上点中线。
- 步 2：路由模块不用改。单台三目设备时所有拍照点都在同一台相机的计划里，按一条触发计数排序；跨相机交错的测试保留给多台设备的情形。
- S7 契约：三个相机槽在单台设备、单路触发时只用槽 1（`cameraShots = [N, 0, 0]`，触发数同理）；有多路触发输入时按实际线路定。计划导出与 S7 文档在第 3 条确认后再改。
- 硬件架构图（`gluesight-hardware-architecture.html`）画的是三台独立相机、三条网线与触发线，与此不符，待线路确认后更新。

### 步 0b · 彩色相机取图（Bayer → 灰度）

- `apply()`：先设 Mono8；相机不支持时，从 `PixelFormat` 可选项里选 8 位 Bayer（BG / RG / GB / GR）。两者都设不上时相机状态为未就绪，原因列出相机支持的格式，不再只记警告。
- 取图回调：Mono8 原样拷贝；8 位 Bayer 按 D-9 转成灰度写进缓冲池；其他格式不静默丢弃，计数并在相机状态里显示"不支持的像素格式 0x…"。预览、整帧、帧录制、示教取图都使用转换后的灰度。
- 转换函数放在独立的纯函数里并单测：纯色块得到 (R+2G+B)/4；四种 Bayer 相位结果一致；边界行列取值不越界；1280 × 1024 单帧耗时记录在测试输出里。
- 完成标准：全量回归通过；模拟 / 回放相机行为不变；用合成 Bayer 帧走取图回调路径得到预期灰度图。真机验证（预览、整帧、标定板识别）列入 W0 台架。

### 步 A · 单帧算法对 MX11 回归（D-10 可行性）

- 数据：MX11 两件 × 43 帧原图，现场系统的结论（Ok / Breaking）与最大、最小胶宽读数作为参考真值（表格只放本机临时目录，客户数据不进仓库）。
- 做法：用 lyFlow glue 包的单帧流程（`bead_path → bead_width → bead_breaks → judge`，`lyflow eval` 批量跑），按 MX11 的相机给胶嘴位置、走向扇区、检测区（离胶嘴约 7 mm 起、长 30–95 mm）、像素当量约 0.112 mm/px；必要时按拍照点给扇区。
- 完成标准：两件全部 86 帧的找胶路率、断胶判定（第二件 47–50 报断胶、其余不报）与现场一致的比例；直线段胶宽与现场读数的偏差；单帧耗时。结论决定步 1b 的配方字段与示教方式；不达标时列出差距与可调的参数，不硬改算法。

### 步 1 · W1 逐拍照点配方契约

- `RecipeDoc` / `Recipe` 增加 `schemaVersion`；`shots` 改为：

  ```rust
  pub struct ShotSpec {
      pub id: String,              // 稳定 ID，如 "P1"，配方内唯一
      pub pose_id: String,         // 现场机器人 / PLC 程序里的 Pose 标识
      pub camera: String,          // 相机编号
      pub center: [f32; 2],        // 视野中心在工件坐标里的位置
      pub fov: Option<[f32; 2]>,   // 缺省用配方的 fov
      pub calib: Option<String>,   // 标定引用，缺省用该相机的工位标定
  }
  ```

- 不兼容旧格式（D-0）：删除顶层 `camera` 与相机序号的旧写法读取；`schemaVersion` 与当前版本不符的配方文件列为加载错误，不迁移；样例配方改为新格式。
- 推导：参与相机（按首次出现顺序）、每台相机负责的拍照点序列、相机内序号与预期帧数。
- 测点归属：在视野包含该测点的拍照点中取中心最近的一个；没有任何拍照点的视野包含它时，配方被拒并报出测点弧长位置。
- 校验：1–64 个拍照点；拍照点 ID 非空、唯一、字符合法；`poseId` 非空但**不要求唯一**（同一 Pose 可同时触发两台相机）；相机编号与标定引用字符合法。
- 标定逐拍照点解析：标定引用缺省为相机编号，对应现有工位标定文件；示教资料里每个拍照点记录自己的标定路径（`VisionAssets.calib` 下沉到 `ShotAssets`）。
- 同一配方的相机来源要一致（全部模拟，或全部真实 / 回放）。
- `geometry_hash` 纳入每个拍照点的全部字段，相机或标定引用一改就需要重新示教（逐拍照点失效在步 5 细化）；去掉 `VisionAssets.camera` 的单独核对。
- `plc_plan.rs` 按各拍照点的相机导出，`PlanShot` 增加 `poseId`（D-7）；`plc-s7-phase1.md` 的示例 JSON 与 hash 同步更新。
- 过渡限制：步 3 完成前，参与相机多于 1 台的配方可以保存、示教、导出计划，但拒绝布防，原因写明"多相机帧归属尚未接入"。
- 分工：后端契约与调用点由主会话完成；前端类型、配方编辑器（每个拍照点的 ID / Pose / 相机 / 视野）与轨迹图逐拍照点视野由子代理在契约固定后完成。
